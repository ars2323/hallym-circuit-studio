# 결정 기록

작업 중 내린 결정을 한 항목씩 남긴다. 형식: 날짜, 결정, 이유, 대안. 새 항목은 아래에 붙인다.

## D-001 머지 전 compat-reviewer 검토

- **날짜:** 2026-09-24
- **결정:** 모든 PR은 `gh pr merge` 전에 `.claude/agents/compat-reviewer.md` 서브에이전트로 diff를 검토한다. 위반이 있으면 고친 뒤 다시 돌린다. 에이전트의 Bash는 PreToolUse 훅(`.claude/hooks/readonly-git-guard.py`)으로 git 읽기 명령만 허용한다.
- **이유:** CLAUDE.md 2절 규칙은 한 번 어기면 채점 연속성과 라이선스 분리가 깨진다. PR을 만든 쪽과 독립된 검토가 필요하다. 서브에이전트 `tools` 필드는 `Bash(git diff:*)` 같은 패턴을 받지 않아 훅으로 제한했다.
- **대안:** Bash를 아예 빼는 것(`git diff`를 볼 수 없어 검토 불가), `permissionMode: plan`(Bash 명령 단위로 좁힐 수 없음).
- **참고:** 에이전트 정의는 세션 시작 때 로드된다. 정의를 추가한 첫 세션에서는 general-purpose 에이전트에 같은 정의 파일을 읽혀 대신 실행했다.

## D-002 저장소와 라이선스

- **날짜:** 2026-09-24
- **결정:** GitHub `ars2323/hallym-circuit-studio`를 private으로 만든다. 라이선스는 GNU GPL 버전 2 이상이고, LICENSE는 2.7.1 jar의 `COPYING.TXT`를 그대로 쓴다.
- **이유:** Logisim 2.7.1 소스 헤더가 "GPL version 2, or (at your option) any later version"이다. 포크는 원본 조건을 따른다. public 전환은 되돌릴 수 없는 사용자 결정이라 `needs-human`에 남긴다.
- **대안:** GPL-3.0-only로 올리기(가능하지만 원본보다 좁힐 이유가 없음).

## D-003 vendor 원본 무결성 검증

- **날짜:** 2026-09-24
- **결정:** `vendor/` 원본의 SHA-256을 `docs/vendor-checksums.sha256`에 기록하고, `tools/verify-vendor.sh`로 CI에서 매번 확인한다. 체크섬 파일은 `vendor/` 밖에 둔다.
- **이유:** 규칙 2.2(vendor 수정 금지)를 사람 눈이 아니라 기계로 지킨다. `vendor/` 안에 파일을 더하는 것 자체가 원본 변경이므로 체크섬은 밖에 둔다.
- **대안:** git 이력만으로 확인(원본이 처음 커밋될 때 이미 바뀌었는지는 알 수 없음).
- **기록:** `logisim-generic-2.7.1.jar` SHA-256 `362a78c12ad18c203fed868872c4a01cd9c12141379d92e892bbe2c37e627bc2`. SPIM 9.1.24는 파일 268개.

## D-004 Actions가 막힌 동안의 머지 기준 (종료)

- **날짜:** 2026-09-24, 갱신 2026-09-24
- **결정(당시):** GitHub Actions가 계정 결제 문제로 시작되지 않는 동안에는, CI와 같은 스크립트 `tools/ci-local.sh`를 로컬에서 돌려 결과를 PR 본문에 붙이고 compat-reviewer 통과 후 머지한다.
- **갱신:** 사용자가 저장소 공개를 확정해 public으로 바꿨고(D-017), 공개 저장소의 Actions가 main에서 성공했다. 이제 머지 기준은 다시 **GitHub CI 통과**다. 워크플로는 검사를 단계별로 나눠 돌린다(vendor, assets, 엔진 소스, hcs-asm, Gradle). `tools/ci-local.sh`는 같은 검사를 로컬에서 재현하는 용도로 남긴다.
- **이유:** "CI 통과 후 머지"의 목적은 같은 검사를 매번 기계로, 기록이 남는 곳에서 돌리는 것이다.
- **대안:** 로컬 스크립트 결과만으로 계속 머지(기록이 PR 본문 글뿐이라 검증할 수 없음).

- **대안:** 회귀 테스트만으로 확인(동작이 우연히 같으면 수정이 숨어 들어옴).

## D-006 .circ 바이트 호환의 검사 기준

- **날짜:** 2026-09-24
- **결정:** 규칙 2.3("새 부품을 안 쓴 .circ는 원조 2.7.1과 바이트 수준으로 호환")은 줄 앞 공백·빈 줄과 한 `<circuit>` 안의 `<wire>`·`<comp>` 순서만 정규화한 뒤 바이트 단위로 같은지로 검사한다. 그 밖의 모든 것(요소·속성 이름, 속성 순서, 값, lib 번호, options, mappings, toolbar)은 그대로 같아야 한다. 기준 출력은 원조 2.7.1을 JDK 8에서 돌려 저장한 결과다.
- **이유:** 원조 2.7.1 자신도 같은 회로를 늘 같은 바이트로 저장하지 않는다. 같은 파일을 원조로 저장해 보면 JDK 8/11/17/21의 출력이 모두 다르다. XML 직렬화기의 들여쓰기가 JDK 9에서 바뀌었고, `Circuit.comps`가 `HashSet<Component>`(identity hash 순서)라 부품 순서가 세션마다 달라질 수 있다. 정규화 없이 비교하면 원조끼리도 실패한다. 같은 JDK에서 반복 저장은 5회 모두 같았다.
- **대안:** 원문 그대로 바이트 비교(원조끼리도 통과 못 함), XML 의미 비교(속성 순서·값 표기 차이를 놓침), 포크의 저장 순서를 정렬(엔진 `file` 패키지 수정이 필요하고 원조와 오히려 달라짐).
- **후속:** 포크 저장 결과 비교 테스트는 #20에서 이 기준으로 만든다. 공백 형식을 JDK 8 쪽에 맞출지(교수·조교가 diff로 볼 때의 잡음)는 #20에서 정한다.
- **보강(2026-09-24, 요구사항 2의 4번):** 정규화 비교에 더해 **의미 동등성 검사**(`tests/regress` `CircEquivalence`)를 함께 돌린다. 두 .circ를 원조 2.7.1로 불러와 옵션, 회로 속성, 부품과 모든 속성 값(`toStandardString`), 넷리스트(원조 연결 계산 + 포트가 선 위에 있으면 연결, 부록 A.4)를 비교한다. 정규화가 속성 변화나 연결 변화를 가리지 않는지 확인하는 용도다. 생성기 일치 테스트와 JAR 라이브러리 재저장 테스트가 두 검사를 모두 통과해야 하고, #20의 포크 저장 비교도 둘 다 쓴다.

## D-007 포크가 MIPS 라이브러리 jar를 찾는 방법

- **날짜:** 2026-09-24
- **결정:** .circ의 `jar#<경로>#kr.ac.hallym.hcs.mips.MipsLibrary`는 (1) 그 경로의 jar를 읽을 수 있으면 원조처럼 그것을 쓰고, (2) 읽을 수 없으면 대화상자 대신 포크에 번들된 `hcs-mips.jar`로 연결한다. 저장할 때는 파일에 있던 설명자 문자열을 유지한다. `Loader.getFileFor()` 한 곳의 격리된 패치로 구현한다(#22, `docs/engine-patches.txt`와 회귀 테스트 필요). 학생에게는 jar를 .circ와 같은 폴더에 두도록 안내한다.
- **이유:** 원조 2.7.1은 jar가 같은 폴더·한 단계 아래·위에 있을 때만 상대 경로로 저장하고 그 밖은 절대 경로로 저장한다. 다른 PC에서 열면 경로가 깨지고 파일 선택 창이 뜬다. 포크 사용자는 jar를 따로 챙기지 않아도 되어야 하고, 같은 파일을 원조로 다시 열 수 있어야 한다. `-sub` 치환은 원래 파일을 먼저 찾은 뒤 적용돼 쓸 수 없고, `getFileFor`는 패키지 전용이라 하위 클래스로 바꿀 수 없다.
- **대안:** 늘 번들 jar를 우선(학생 폴더의 옛 jar와 동작이 갈릴 때 원조와 결과가 달라짐), 포크가 열 때 jar를 .circ 옆에 복사(학생 폴더에 몰래 파일을 만듦), 번들 라이브러리를 내장 라이브러리로 등록(설명자가 `#이름`이 되어 원조에서 열리지 않음).

## D-009 hcs-asm의 라이선스

- **날짜:** 2026-09-24
- **결정:** `native/hcs-asm/`은 GPL이 아니라 SPIM과 같은 BSD 3-Clause로 둔다(`native/hcs-asm/LICENSE`). Java 쪽은 `hcs-asm`을 별도 프로세스로만 실행한다.
- **이유:** 규칙 2.5(SPIM 코드는 GPL 코드와 섞지 않는다). `hcs-asm`은 SPIM 코어를 링크하고 `read_assembly_file()`의 몇 줄을 따라 쓴다. BSD 코드만으로 이루어진 실행 파일로 두면 라이선스 경계가 프로세스 경계와 같아진다.
- **대안:** GPL로 두기(BSD 코드와 결합은 가능하지만, SPIM 쪽 코드가 GPL 저장소 조건에 묶여 경계가 흐려짐).

## D-010 기계어는 QtSpim 그대로 (사용자 확정)

- **날짜:** 2026-09-24, 개정 2026-09-24(사용자 확정)
- **결정:** QtSpim 기계어를 그대로 올린다. 도구는 인코딩과 분기 계산에 관여하지 않는다. hcs-asm은 QtSpim·Hallym MIPS 기본 설정(예외 처리기 끔, 지연 분기 끔, 의사 명령어 켬)으로 어셈블한 워드를 그대로 내고, 인코딩을 고르는 옵션도 두지 않는다. 주소·기계어·명령어 이름 표시는 Hallym MIPS와 모든 명령에서 비트 단위로 같아야 한다.
- **이유:** 도구는 부품 라이브러리와 편집 도구를 줄 뿐 학생 설계에 관여하지 않는다(PLAN.md 1장 설계 원칙, CLAUDE.md 2절). 분기 목적지 계산은 학생 데이터패스의 몫이다.
- **참고 사실(0단계 조사):** 지연 분기를 끈 SPIM은 분기 오프셋을 PC 기준 `(목적지 − PC)/4`로, 켜면 PC+4 기준으로 인코딩한다. 교재 설명은 PC+4 기준이다. 어셈블 단계에서 이 설정이 바꾸는 것은 분기 오프셋 하나다(`CPU/sym-tbl.cpp:264`).
- **검증:** hcs-asm 골든과 원본 spim 오라클(지연 분기 끔), 원본 QtSpim GUI 출력 골든(`tests/asm/qtspim/`)이 분기를 포함해 모두 같다.
- **대안(버림):** 처음에는 분기 오프셋만 교재 정의로 다시 인코딩했다(`-branch pc4`). 사용자가 "QtSpim과 무조건 동일"로 확정해 코드를 모두 지웠다.

## D-011 식별요소 가져오기와 앱 아이콘

- **날짜:** 2026-09-24
- **결정:** `assets/`의 글꼴·로고·캐릭터는 `tools/import-assets.py`가 원본 zip과 Hallym MIPS `brand/`에서 꺼내거나 복사만 해서 만든다. `assets/MANIFEST.sha256`과 `tools/verify-assets.sh`로 CI에서 바이트 일치를 확인하고, `.ai`·`.eps`·`.psd`·가이드라인 PDF가 git에 들어오면 실패시킨다. 앱 아이콘은 Hallym MIPS와 같은 파일(흰 타일 + 심볼 기본형)을 쓴다.
- **이유:** 규칙 2.4(원형 그대로)를 사람 눈이 아니라 기계로 지킨다. 이미지를 열어 다시 저장하면 픽셀이 같아도 바이트가 달라져 가공 여부를 가릴 수 없으므로 아예 열지 않는다. 앱 아이콘은 Hallym MIPS 선례를 따르라는 CLAUDE.md 8절에 맞춘다. 두 제품을 한 PC에서 함께 쓸 때 작업 표시줄에서 구분이 어려울 수 있지만, 마크에 요소를 더해 구분하는 것은 규정 위반이라 이름(창 제목)으로 구분한다.
- **대안:** Ghostscript로 `.ai`를 다시 렌더링(Hallym MIPS 결과와 미세하게 달라짐), 제품별로 다른 타일 색(학교 규정 해석이 필요해 보류).

## D-012 엔진 회귀 테스트의 기준과 회로 생성

- **날짜:** 2026-09-24
- **결정:** 엔진 회귀의 기대값은 표준 2.7.1 jar를 JDK 8에서 `-tty table`로 돌린 출력이다(`tests/circ/*.expected`). 회로는 손으로 쓰지 않고 `tests/regress`의 생성기가 원조 2.7.1 API로 만들어 원조의 저장 코드로 저장한다. 연결은 포트 위 라벨 터널로 한다. `CircNormalizer`는 `:regress`에 두고 `lib-mips` 테스트도 같이 쓴다.
- **이유:** 학생 PC의 원조 2.7.1은 Java 8에서 도는 경우가 많고, 이 조건의 결과가 채점 기준이다. 포트 좌표를 손으로 계산하면 부품·속성마다 달라 틀리기 쉽다(PLAN.md 부록 A.3의 과거 실패). 부품에서 받은 좌표와 터널을 쓰면 회로가 의도한 연결 그대로다.
- **대안:** .circ를 손으로 작성(좌표 오류 위험), 선으로만 연결(교차·겹침 규칙 때문에 의도치 않은 합선 위험), 실제 과제 세트만 사용(아직 없음, #54).

## D-013 MIPS 메모리 부품의 저장 이름과 동작

- **날짜:** 2026-09-24
- **결정:** 부품 이름 `Instruction Memory`, `Data Memory`, `Stack`, 포트 순서·좌표(`docs/mips-components.md`), 속성 이름 `base`, `size`, `contents`, `source`, `label`로 확정한다. 초기 내용은 `hcs-words 1` 텍스트 형식으로 저장한다. 읽지 않을 때와 영역 밖에서는 출력을 구동하지 않고, 정의되지 않은 값을 쓴 칸은 x로 읽는다. 떠 있는 제어 입력은 동작하지 않고 부품 안에 표시한다.
- **이유:** 이름과 포트 좌표는 .circ에 저장돼 배포 뒤 바꾸면 기존 파일이 깨진다. 트랙 A는 원조 2.7.1에서도 돌아야 하므로 진단 패널 없이 부품 스스로 문제를 보여야 한다. 구동하지 않는 방식은 Logisim에서 두 출력을 한 선에 이을 때 충돌 없이 합쳐지는 유일한 방법이다(PLAN.md 6.2 "영역 밖 주소에서는 출력하지 않는다"). x 기록을 보존해야 4단계에서 "X가 메모리에 기록됨"을 찾을 수 있다.
- **대안:** 원조 ROM의 `addr/data:` 형식 재사용(주소 폭이 24비트까지이고 0번지부터라 32비트 희소 주소를 담지 못함), 떠 있는 제어 입력을 원조 RAM처럼 1로 처리(PLAN.md가 금지), 정의되지 않은 쓰기를 무시(오류의 흔적이 사라짐).

## D-014 Console의 Exit 출력과 print_string 읽기

- **날짜:** 2026-09-24
- **결정:** Console에 PLAN.md 6.9의 네 입력 외에 출력 `Exit`(exit 뒤 1)를 둔다. print_string은 같은 프로젝트의 Data Memory·Stack이 전파될 때 스스로 등록하는 `MemoryRegistry`를 통해 바이트를 읽고, 바이트열은 UTF-8로 해석한다.
- **이유:** 원조 2.7.1 `-tty` 모드는 `halt` 출력 핀으로만 멈춘다. GUI에서는 exit가 클럭 틱을 멈추지만 명령줄·채점 스크립트에서도 프로그램 끝에서 멈추려면 핀이 필요하다. 원조에는 다른 부품의 상태를 얻는 공개 API가 없고(`InstanceStateImpl`, `CircuitState` 접근이 패키지 전용), 엔진을 고치지 않으려면 메모리 쪽이 알려 주는 방식뿐이다. .s는 UTF-8로 저장되므로 한글 문자열이 깨지지 않게 UTF-8로 읽는다.
- **대안:** `Exit` 없이 GUI에서만 멈춤(명령줄 채점 불가), 원조 TTY 부품처럼 `-tty tty` 출력(원조가 자기 TTY 클래스만 찾아 불가), 바이트를 ISO-8859-1로 해석(SPIM 콘솔과 같지만 한글이 깨짐).

## D-015 .s 불러오기의 대상 결정과 명령어 이름

- **날짜:** 2026-09-24
- **결정:** 우클릭한 메모리가 자기 세그먼트를 받고, 다른 세그먼트는 파일 전체 회로에서 찾아 후보가 여럿일 때만 묻는다. .data는 Stack에 넣지 않는다. `source`는 .circ 아래면 상대 경로, 아니면 절대 경로로 저장한다. 명령어 이름은 MIPS32 명세로 직접 쓴 `Disassembler`가 정하고 부동소수점은 다루지 않는다. `hcs-asm`은 jar 옆에서 찾는다.
- **이유:** PLAN.md 6.3 "같은 부품이 둘 이상일 때만 어느 쪽인지 묻는다". 메모리는 흔히 datapath 서브회로 안에 있어 현재 회로만 보면 못 찾는다. 사용 명령어 목록(6.6)은 기계어에서 나와야 의사 명령어가 펼쳐진 실제 명령어가 보인다. SPIM의 op.h를 옮기면 BSD 코드가 GPL 쪽에 섞이므로 명세에서 새로 쓰고 원본 spim 출력과 대조했다. 수업 데이터패스에는 부동소수점이 없다.
- **대안:** 명령어 목록을 hcs-asm JSON에 넣기(SPIM 이름표가 필요 없지만, 사이클 뷰·명령어 필드 표시에서 Java 쪽 디코더가 어차피 필요), 현재 회로에서만 찾기(서브회로 속 메모리를 놓침), 상대 경로만 저장(다른 폴더의 .s를 쓸 수 없음).

## D-016 편집기 개선 요구사항과 단계 재배치

- **날짜:** 2026-09-24(요구사항 접수, 1단계 진행 중)
- **결정:** 사용자의 편집기 개선 요구사항(A 창 구조와 탭 ~ N 화면)을 PLAN.md 11장으로 옮기고 이번 범위에 넣는다. 마일스톤 `2 포크 + 정적 진단`을 `2a 포크 + 편집기 기반`, `2b 편집 핵심`, `2c 정적 진단 + 배선`으로 나누고 `4b 편의 마무리`를 더한다. 기존 2단계의 열린 이슈는 2a(빌드·엔진 회귀·바이트 호환·FlatLaf·번들·리소스 번들·배포)와 2b(공용 식별자·등록표), 2c(정적 진단·고장 회로·Messages·MIPS 진단·관련 질문)로 옮긴다.
- **이유:**
  - 창 구조와 탭(A)을 가장 먼저 둔다. 되돌리기·시뮬레이션·사이클 뷰·진단이 탭마다 따로여야 해서, 탭 없이 만든 UI는 나중에 다시 짜야 한다.
  - 편집 핵심(2b)을 정적 진단(2c)보다 앞에 둔다. Messages 탭, 부품 하이라이트, 클릭 이동 같은 진단 표시가 편집기 틀(탭, 확대, 우클릭, 상태 표시줄) 위에서 동작하기 때문이다. 공용 식별자(`datapath › PC`)는 마우스 오버 정보가 먼저 쓰므로 2b로 옮긴다.
  - 연결 탐색 엔진은 2b에서 만든다. 마우스 오버의 넷 이름이 처음 쓰고, 2c의 영향 경로·배선 진단·포트 변경 영향, 4단계의 E·X 추적이 같은 엔진을 쓴다(11.0).
  - 탭 간 라이브러리와 저장 반영(A 일부)은 2c다. 포트 변경 영향과 끊긴 연결 진단이 연결 탐색 엔진과 정적 진단을 필요로 한다.
  - 버스 값 표시·활성 경로는 기록 엔진·사이클 뷰가 있어야 해서 3단계다.
  - 없어도 수업이 되는 편의 기능(H, 스플리터 편집기, 제출 파일, 그림 내보내기, 미니맵 등)은 4b로 미룬다.
- **호환:** 요구사항의 "원조 2.7.1과 바이트 수준 호환"은 D-006의 검사 기준(줄 앞 공백·wire/comp 순서만 정규화)으로 확인한다. 툴바·마우스 매핑·라벨 글꼴은 .circ 밖(앱 환경설정)에 두고, 터널 색·신호 그룹·영역 메모만 7.0 네임스페이스로 저장한다.
- **대안:** 기존 2단계를 그대로 두고 편집기 개선을 5단계 뒤에 붙이기(진단 UI를 편집기 틀 없이 먼저 만들었다가 다시 짜야 함), 편집기 개선을 한 마일스톤으로 묶기(너무 커서 단계마다 쓸 수 있는 상태로 끊을 수 없음).
