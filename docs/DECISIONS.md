# 결정 기록

작업 중 내린 결정을 한 항목씩 남긴다. 형식: 날짜, 결정, 이유, 대안. 새 항목은 아래에 붙인다.

## D-001 머지 전 compat-reviewer 검토

- **날짜:** 2026-09-24
- **결정:** 모든 PR은 `gh pr merge` 전에 `.claude/agents/compat-reviewer.md` 서브에이전트로 diff를 검토한다. 위반이 있으면 고친 뒤 다시 돌린다. 에이전트의 Bash는 PreToolUse 훅(`.claude/hooks/readonly-git-guard.py`)으로 git 읽기 명령만 허용한다.
- **이유:** CLAUDE.md 2절 규칙은 한 번 어기면 채점 연속성과 라이선스 분리가 깨진다. PR을 만든 쪽과 독립된 검토가 필요하다. 서브에이전트 `tools` 필드는 `Bash(git diff:*)` 같은 패턴을 받지 않아 훅으로 제한했다.
- **대안:** Bash를 아예 빼는 것(`git diff`를 볼 수 없어 검토 불가), `permissionMode: plan`(Bash 명령 단위로 좁힐 수 없음).
- **참고:** 에이전트 정의는 세션 시작 때 로드된다. 정의를 추가한 첫 세션에서는 general-purpose 에이전트에 같은 정의 파일을 읽혀 대신 실행했다.

## D-002 저장소와 라이선스

- **날짜:** 2026-09-24
- **결정:** GitHub `ars2323/hallym-circuit-studio`를 private으로 만든다. 라이선스는 GNU GPL 버전 2 이상이고, LICENSE는 2.7.1 jar의 `COPYING.TXT`를 그대로 쓴다.
- **이유:** Logisim 2.7.1 소스 헤더가 "GPL version 2, or (at your option) any later version"이다. 포크는 원본 조건을 따른다. public 전환은 되돌릴 수 없는 사용자 결정이라 `needs-human`에 남긴다.
- **대안:** GPL-3.0-only로 올리기(가능하지만 원본보다 좁힐 이유가 없음).

## D-003 vendor 원본 무결성 검증

- **대안:** git 이력만으로 확인(원본이 처음 커밋될 때 이미 바뀌었는지는 알 수 없음).
- **기록:** `logisim-generic-2.7.1.jar` SHA-256 `362a78c12ad18c203fed868872c4a01cd9c12141379d92e892bbe2c37e627bc2`. SPIM 9.1.24는 파일 268개.

## D-004 Actions가 막힌 동안의 머지 기준 (종료)

- **날짜:** 2026-09-24, 갱신 2026-09-24
- **결정(당시):** GitHub Actions가 계정 결제 문제로 시작되지 않는 동안에는, CI와 같은 스크립트 `tools/ci-local.sh`를 로컬에서 돌려 결과를 PR 본문에 붙이고 compat-reviewer 통과 후 머지한다.
- **갱신:** 사용자가 저장소 공개를 확정해 public으로 바꿨고(D-017), 공개 저장소의 Actions가 main에서 성공했다. 이제 머지 기준은 다시 **GitHub CI 통과**다. 워크플로는 검사를 단계별로 나눠 돌린다(vendor, assets, 엔진 소스, hcs-asm, Gradle). `tools/ci-local.sh`는 같은 검사를 로컬에서 재현하는 용도로 남긴다.
- **이유:** "CI 통과 후 머지"의 목적은 같은 검사를 매번 기계로, 기록이 남는 곳에서 돌리는 것이다.
- **대안:** 로컬 스크립트 결과만으로 계속 머지(기록이 PR 본문 글뿐이라 검증할 수 없음).

## D-006 .circ 바이트 호환의 검사 기준

- **날짜:** 2026-09-24
- **결정:** 규칙 2.3("새 부품을 안 쓴 .circ는 원조 2.7.1과 바이트 수준으로 호환")은 줄 앞 공백·빈 줄과 한 `<circuit>` 안의 `<wire>`·`<comp>` 순서만 정규화한 뒤 바이트 단위로 같은지로 검사한다. 그 밖의 모든 것(요소·속성 이름, 속성 순서, 값, lib 번호, options, mappings, toolbar)은 그대로 같아야 한다. 기준 출력은 원조 2.7.1을 JDK 8에서 돌려 저장한 결과다.
- **이유:** 원조 2.7.1 자신도 같은 회로를 늘 같은 바이트로 저장하지 않는다. 같은 파일을 원조로 저장해 보면 JDK 8/11/17/21의 출력이 모두 다르다. XML 직렬화기의 들여쓰기가 JDK 9에서 바뀌었고, `Circuit.comps`가 `HashSet<Component>`(identity hash 순서)라 부품 순서가 세션마다 달라질 수 있다. 정규화 없이 비교하면 원조끼리도 실패한다. 같은 JDK에서 반복 저장은 5회 모두 같았다.
- **대안:** 원문 그대로 바이트 비교(원조끼리도 통과 못 함), XML 의미 비교(속성 순서·값 표기 차이를 놓침), 포크의 저장 순서를 정렬(엔진 `file` 패키지 수정이 필요하고 원조와 오히려 달라짐).
- **후속:** 포크 저장 결과 비교 테스트는 #20에서 이 기준으로 만든다. 공백 형식을 JDK 8 쪽에 맞출지(교수·조교가 diff로 볼 때의 잡음)는 #20에서 정한다.
- **보강(2026-09-24, 요구사항 2의 4번):** 정규화 비교에 더해 **의미 동등성 검사**(`tests/regress` `CircEquivalence`)를 함께 돌린다. 두 .circ를 원조 2.7.1로 불러와 옵션, 회로 속성, 부품과 모든 속성 값(`toStandardString`), 넷리스트(원조 연결 계산 + 포트가 선 위에 있으면 연결, 부록 A.4)를 비교한다. 정규화가 속성 변화나 연결 변화를 가리지 않는지 확인하는 용도다. 생성기 일치 테스트와 JAR 라이브러리 재저장 테스트가 두 검사를 모두 통과해야 하고, #20의 포크 저장 비교도 둘 다 쓴다.

## D-007 포크가 MIPS 라이브러리 jar를 찾는 방법

- **날짜:** 2026-09-24
- **결정:** .circ의 `jar#<경로>#kr.ac.hallym.hcs.mips.MipsLibrary`는 (1) 그 경로의 jar를 읽을 수 있으면 원조처럼 그것을 쓰고, (2) 읽을 수 없으면 대화상자 대신 포크에 번들된 `hcs-mips.jar`로 연결한다. 저장할 때는 파일에 있던 설명자 문자열을 유지한다. `Loader.getFileFor()` 한 곳의 격리된 패치로 구현한다(#22, `docs/engine-patches.txt`와 회귀 테스트 필요). 학생에게는 jar를 .circ와 같은 폴더에 두도록 안내한다.
- **이유:** 원조 2.7.1은 jar가 같은 폴더·한 단계 아래·위에 있을 때만 상대 경로로 저장하고 그 밖은 절대 경로로 저장한다. 다른 PC에서 열면 경로가 깨지고 파일 선택 창이 뜬다. 포크 사용자는 jar를 따로 챙기지 않아도 되어야 하고, 같은 파일을 원조로 다시 열 수 있어야 한다. `-sub` 치환은 원래 파일을 먼저 찾은 뒤 적용돼 쓸 수 없고, `getFileFor`는 패키지 전용이라 하위 클래스로 바꿀 수 없다.
- **대안:** 늘 번들 jar를 우선(학생 폴더의 옛 jar와 동작이 갈릴 때 원조와 결과가 달라짐), 포크가 열 때 jar를 .circ 옆에 복사(학생 폴더에 몰래 파일을 만듦), 번들 라이브러리를 내장 라이브러리로 등록(설명자가 `#이름`이 되어 원조에서 열리지 않음).
- **보강(#22 구현):** 패치 자리는 `Loader.getFileFor`가 아니라 `LibraryManager`다. getFileFor가 번들 jar를 돌려주면 저장 설명자가 번들 jar 경로가 되어 "설명자 유지"를 못 지킨다. `LibraryManager.loadLibrary`의 jar 분기에서 .circ가 가리키는 파일(named)을 읽을 수 없고 클래스가 번들된 라이브러리일 때만, `JarDescriptor`에 저장용 경로(named)와 불러올 jar(source)를 따로 넣는다. 그 밖의 경우는 원조 코드 경로 그대로다. 번들 위치는 포크 jar 옆 `lib/hcs-mips.jar`(hcs-asm도 같은 `lib/`)이고, 판단은 `kr.ac.hallym.hcs.app.BundledLibraries` 한 곳에 둔다. `BundledLibraryTest`가 번들 연결·설명자 유지(상대·다른 PC 절대 경로)·D-006 동등, 경로의 jar가 있을 때 원조 동작, 다른 라이브러리·번들 없음일 때 원조처럼 파일 선택 창을 띄우려는 것을 확인한다.

## D-009 hcs-asm의 라이선스

- **날짜:** 2026-09-24
- **결정:** `native/hcs-asm/`은 GPL이 아니라 SPIM과 같은 BSD 3-Clause로 둔다(`native/hcs-asm/LICENSE`). Java 쪽은 `hcs-asm`을 별도 프로세스로만 실행한다.
- **이유:** 규칙 2.5(SPIM 코드는 GPL 코드와 섞지 않는다). `hcs-asm`은 SPIM 코어를 링크하고 `read_assembly_file()`의 몇 줄을 따라 쓴다. BSD 코드만으로 이루어진 실행 파일로 두면 라이선스 경계가 프로세스 경계와 같아진다.
- **대안:** GPL로 두기(BSD 코드와 결합은 가능하지만, SPIM 쪽 코드가 GPL 저장소 조건에 묶여 경계가 흐려짐).

## D-010 기계어는 QtSpim 그대로 (사용자 확정)

- **날짜:** 2026-09-24, 개정 2026-09-24(사용자 확정)
- **결정:** QtSpim 기계어를 그대로 올린다. 도구는 인코딩과 분기 계산에 관여하지 않는다. hcs-asm은 QtSpim·Hallym MIPS 기본 설정(예외 처리기 끔, 지연 분기 끔, 의사 명령어 켬)으로 어셈블한 워드를 그대로 내고, 인코딩을 고르는 옵션도 두지 않는다. 주소·기계어·명령어 이름 표시는 Hallym MIPS와 모든 명령에서 비트 단위로 같아야 한다.
- **이유:** 도구는 부품 라이브러리와 편집 도구를 줄 뿐 학생 설계에 관여하지 않는다(PLAN.md 1장 설계 원칙, CLAUDE.md 2절). 분기 목적지 계산은 학생 데이터패스의 몫이다.
- **참고 사실(0단계 조사):** 지연 분기를 끈 SPIM은 분기 오프셋을 PC 기준 `(목적지 − PC)/4`로, 켜면 PC+4 기준으로 인코딩한다. 교재 설명은 PC+4 기준이다. 어셈블 단계에서 이 설정이 바꾸는 것은 분기 오프셋 하나다(`CPU/sym-tbl.cpp:264`).
- **검증:** hcs-asm 골든과 원본 spim 오라클(지연 분기 끔), 원본 QtSpim GUI 출력 골든(`tests/asm/qtspim/`)이 분기를 포함해 모두 같다.
- **대안(버림):** 처음에는 분기 오프셋만 교재 정의로 다시 인코딩했다(`-branch pc4`). 사용자가 "QtSpim과 무조건 동일"로 확정해 코드를 모두 지웠다.

## D-011 식별요소 가져오기와 앱 아이콘

- **날짜:** 2026-09-24
- **결정:** `assets/`의 글꼴·로고·캐릭터는 `tools/import-assets.py`가 원본 zip과 Hallym MIPS `brand/`에서 꺼내거나 복사만 해서 만든다. `assets/MANIFEST.sha256`과 `tools/verify-assets.sh`로 CI에서 바이트 일치를 확인하고, `.ai`·`.eps`·`.psd`·가이드라인 PDF가 git에 들어오면 실패시킨다. 앱 아이콘은 Hallym MIPS와 같은 파일(흰 타일 + 심볼 기본형)을 쓴다.
- **이유:** 규칙 2.4(원형 그대로)를 사람 눈이 아니라 기계로 지킨다. 이미지를 열어 다시 저장하면 픽셀이 같아도 바이트가 달라져 가공 여부를 가릴 수 없으므로 아예 열지 않는다. 앱 아이콘은 Hallym MIPS 선례를 따르라는 CLAUDE.md 8절에 맞춘다. 두 제품을 한 PC에서 함께 쓸 때 작업 표시줄에서 구분이 어려울 수 있지만, 마크에 요소를 더해 구분하는 것은 규정 위반이라 이름(창 제목)으로 구분한다.
- **대안:** Ghostscript로 `.ai`를 다시 렌더링(Hallym MIPS 결과와 미세하게 달라짐), 제품별로 다른 타일 색(학교 규정 해석이 필요해 보류).

## D-012 엔진 회귀 테스트의 기준과 회로 생성

- **날짜:** 2026-09-24
- **결정:** 엔진 회귀의 기대값은 표준 2.7.1 jar를 JDK 8에서 `-tty table`로 돌린 출력이다(`tests/circ/*.expected`). 회로는 손으로 쓰지 않고 `tests/regress`의 생성기가 원조 2.7.1 API로 만들어 원조의 저장 코드로 저장한다. 연결은 포트 위 라벨 터널로 한다. `CircNormalizer`는 `:regress`에 두고 `lib-mips` 테스트도 같이 쓴다.
- **이유:** 학생 PC의 원조 2.7.1은 Java 8에서 도는 경우가 많고, 이 조건의 결과가 채점 기준이다. 포트 좌표를 손으로 계산하면 부품·속성마다 달라 틀리기 쉽다(PLAN.md 부록 A.3의 과거 실패). 부품에서 받은 좌표와 터널을 쓰면 회로가 의도한 연결 그대로다.
- **대안:** .circ를 손으로 작성(좌표 오류 위험), 선으로만 연결(교차·겹침 규칙 때문에 의도치 않은 합선 위험), 실제 과제 세트만 사용(아직 없음, #54).

## D-013 MIPS 메모리 부품의 저장 이름과 동작

- **날짜:** 2026-09-24
- **결정:** 부품 이름 `Instruction Memory`, `Data Memory`, `Stack`, 포트 순서·좌표(`docs/mips-components.md`), 속성 이름 `base`, `size`, `contents`, `source`, `label`로 확정한다. 초기 내용은 `hcs-words 1` 텍스트 형식으로 저장한다. 읽지 않을 때와 영역 밖에서는 출력을 구동하지 않고, 정의되지 않은 값을 쓴 칸은 x로 읽는다. 떠 있는 제어 입력은 동작하지 않고 부품 안에 표시한다.
- **이유:** 이름과 포트 좌표는 .circ에 저장돼 배포 뒤 바꾸면 기존 파일이 깨진다. 트랙 A는 원조 2.7.1에서도 돌아야 하므로 진단 패널 없이 부품 스스로 문제를 보여야 한다. 구동하지 않는 방식은 Logisim에서 두 출력을 한 선에 이을 때 충돌 없이 합쳐지는 유일한 방법이다(PLAN.md 6.2 "영역 밖 주소에서는 출력하지 않는다"). x 기록을 보존해야 4단계에서 "X가 메모리에 기록됨"을 찾을 수 있다.
- **대안:** 원조 ROM의 `addr/data:` 형식 재사용(주소 폭이 24비트까지이고 0번지부터라 32비트 희소 주소를 담지 못함), 떠 있는 제어 입력을 원조 RAM처럼 1로 처리(PLAN.md가 금지), 정의되지 않은 쓰기를 무시(오류의 흔적이 사라짐).

## D-014 Console의 Exit 출력과 print_string 읽기

- **날짜:** 2026-09-24
- **결정:** Console에 PLAN.md 6.9의 네 입력 외에 출력 `Exit`(exit 뒤 1)를 둔다. print_string은 같은 프로젝트의 Data Memory·Stack이 전파될 때 스스로 등록하는 `MemoryRegistry`를 통해 바이트를 읽고, 바이트열은 UTF-8로 해석한다.
- **이유:** 원조 2.7.1 `-tty` 모드는 `halt` 출력 핀으로만 멈춘다. GUI에서는 exit가 클럭 틱을 멈추지만 명령줄·채점 스크립트에서도 프로그램 끝에서 멈추려면 핀이 필요하다. 원조에는 다른 부품의 상태를 얻는 공개 API가 없고(`InstanceStateImpl`, `CircuitState` 접근이 패키지 전용), 엔진을 고치지 않으려면 메모리 쪽이 알려 주는 방식뿐이다. .s는 UTF-8로 저장되므로 한글 문자열이 깨지지 않게 UTF-8로 읽는다.
- **대안:** `Exit` 없이 GUI에서만 멈춤(명령줄 채점 불가), 원조 TTY 부품처럼 `-tty tty` 출력(원조가 자기 TTY 클래스만 찾아 불가), 바이트를 ISO-8859-1로 해석(SPIM 콘솔과 같지만 한글이 깨짐).

## D-015 .s 불러오기의 대상 결정과 명령어 이름

- **날짜:** 2026-09-24
- **결정:** 우클릭한 메모리가 자기 세그먼트를 받고, 다른 세그먼트는 파일 전체 회로에서 찾아 후보가 여럿일 때만 묻는다. .data는 Stack에 넣지 않는다. `source`는 .circ 아래면 상대 경로, 아니면 절대 경로로 저장한다. 명령어 이름은 MIPS32 명세로 직접 쓴 `Disassembler`가 정하고 부동소수점은 다루지 않는다. `hcs-asm`은 jar 옆에서 찾는다.
- **이유:** PLAN.md 6.3 "같은 부품이 둘 이상일 때만 어느 쪽인지 묻는다". 메모리는 흔히 datapath 서브회로 안에 있어 현재 회로만 보면 못 찾는다. 사용 명령어 목록(6.6)은 기계어에서 나와야 의사 명령어가 펼쳐진 실제 명령어가 보인다. SPIM의 op.h를 옮기면 BSD 코드가 GPL 쪽에 섞이므로 명세에서 새로 쓰고 원본 spim 출력과 대조했다. 수업 데이터패스에는 부동소수점이 없다.
- **대안:** 명령어 목록을 hcs-asm JSON에 넣기(SPIM 이름표가 필요 없지만, 사이클 뷰·명령어 필드 표시에서 Java 쪽 디코더가 어차피 필요), 현재 회로에서만 찾기(서브회로 속 메모리를 놓침), 상대 경로만 저장(다른 폴더의 .s를 쓸 수 없음).

## D-016 편집기 개선 요구사항과 단계 재배치

- **날짜:** 2026-09-24(요구사항 접수, 1단계 진행 중)
- **결정:** 사용자의 편집기 개선 요구사항(A 창 구조와 탭 ~ N 화면)을 PLAN.md 11장으로 옮기고 이번 범위에 넣는다. 마일스톤 `2 포크 + 정적 진단`을 `2a 포크 + 편집기 기반`, `2b 편집 핵심`, `2c 정적 진단 + 배선`으로 나누고 `4b 편의 마무리`를 더한다. 기존 2단계의 열린 이슈는 2a(빌드·엔진 회귀·바이트 호환·FlatLaf·번들·리소스 번들·배포)와 2b(공용 식별자·등록표), 2c(정적 진단·고장 회로·Messages·MIPS 진단·관련 질문)로 옮긴다.
- **이유:**
  - 창 구조와 탭(A)을 가장 먼저 둔다. 되돌리기·시뮬레이션·사이클 뷰·진단이 탭마다 따로여야 해서, 탭 없이 만든 UI는 나중에 다시 짜야 한다.
  - 편집 핵심(2b)을 정적 진단(2c)보다 앞에 둔다. Messages 탭, 부품 하이라이트, 클릭 이동 같은 진단 표시가 편집기 틀(탭, 확대, 우클릭, 상태 표시줄) 위에서 동작하기 때문이다. 공용 식별자(`datapath › PC`)는 마우스 오버 정보가 먼저 쓰므로 2b로 옮긴다.
  - 연결 탐색 엔진은 2b에서 만든다. 마우스 오버의 넷 이름이 처음 쓰고, 2c의 영향 경로·배선 진단·포트 변경 영향, 4단계의 E·X 추적이 같은 엔진을 쓴다(11.0).
  - 탭 간 라이브러리와 저장 반영(A 일부)은 2c다. 포트 변경 영향과 끊긴 연결 진단이 연결 탐색 엔진과 정적 진단을 필요로 한다.
  - 버스 값 표시·활성 경로는 기록 엔진·사이클 뷰가 있어야 해서 3단계다.
  - 없어도 수업이 되는 편의 기능(H, 스플리터 편집기, 제출 파일, 그림 내보내기, 미니맵 등)은 4b로 미룬다.
- **호환:** 요구사항의 "원조 2.7.1과 바이트 수준 호환"은 D-006의 검사 기준(줄 앞 공백·wire/comp 순서만 정규화)으로 확인한다. 툴바·마우스 매핑·라벨 글꼴은 .circ 밖(앱 환경설정)에 두고, 터널 색·신호 그룹·영역 메모만 7.0 네임스페이스로 저장한다.
- **대안:** 기존 2단계를 그대로 두고 편집기 개선을 5단계 뒤에 붙이기(진단 UI를 편집기 틀 없이 먼저 만들었다가 다시 짜야 함), 편집기 개선을 한 마일스톤으로 묶기(너무 커서 단계마다 쓸 수 있는 상태로 끊을 수 없음).

## D-018 Data·Stack의 자라는 방향과 영역 진단

- **날짜:** 2026-09-24(요구사항 2의 6번)
- **결정:** Data Memory는 `base` 0x10010000부터 높은 주소 쪽으로, Stack은 새 속성 `top` 0x7FFFFFFC(맨 위 워드)부터 낮은 주소 쪽으로 자라고, 한계 `size`는 둘 다 기본 1MB다. Stack은 `base` 속성을 없애고 `top`을 둔다(v0.1.0 전이라 저장된 파일이 없다). 영역 밖은 구동·쓰기를 하지 않는다. 동작하지 않는 경우(떠 있는 제어 입력, 정렬 안 된 주소, 어느 영역에도 없는 주소, Stack 한계 바로 아래, 영역 겹침)만 부품 안에 알리고 상태에 둔다. "스택 사용량이 한계를 넘었습니다"는 Stack 영역 바로 아래 한계 폭만큼의 주소에 접근할 때다. 그보다 아래는 "어느 영역에도 없는 주소"다. Stack 깊이는 접근한 주소로 센다.
- **이유:** 제품 원칙(PLAN.md 1장)대로 동작하지 않는 경우만 사실로 알린다. 부품은 `$sp`를 모르므로 "한계를 넘었다"는 한계 바로 아래 접근이라는 관찰한 사실로만 판정하고, 폭은 한계와 같게 해 규칙을 하나로 둔다. 레지스트리는 부품 인스턴스마다 최신 상태 하나만 둬서, 리셋 전 상태 때문에 겹침을 잘못 알리지 않는다.
- **대안:** `$sp` 입력 포트를 Stack에 추가(포트가 늘고 PLAN 6.2 포트 정의와 달라짐, 메모리 패널이 레지스터 파일에서 알 수 있음), 두 영역 사이 전체를 스택 초과로 보기(Data 쪽 잘못된 주소까지 스택 탓이 됨).

## D-019 제품 원칙: 동작하지 않는 회로만 알린다

- **날짜:** 2026-09-24(요구사항 2의 0번·5번)
- **결정:** 도구는 (1) 부품 라이브러리와 편집 도구를 주고 (2) "동작하지 않는 회로"만 알린다. "동작하지만 잘못된 회로"는 판단하지도, 고치지도, 정답과 비교하지도 않는다. 학생 설계에 관여하지 않는다. PLAN.md 1장 설계 원칙과 CLAUDE.md 2절 규칙 6에 적고, compat-reviewer에 검사 7로 넣는다.
- **이 원칙으로 바꾼 것:**
  - "선이 남의 포트 위를 지나가 연결됐습니다" 진단을 없앴다. 연결점을 크게 그리는 화면 표시만 남긴다(그로 인한 합선은 합선 진단이 잡는다). #82 수정.
  - 미결정이던 "게이트로 만든 클럭 경고"(#48)와 "SPIM 정답 레지스터 값 공개"(#47)는 원칙 밖이라 하지 않는다. 두 이슈를 닫았다.
  - 분기 인코딩은 QtSpim 그대로(D-010).
- **유지:** 동작하지 않는 경우(어느 메모리 영역에도 없는 주소, 워드 정렬 안 된 주소, 스택 한계 초과, Data·Stack 영역 겹침, 떠 있는 MemWrite·MemRead·Syscall, PLAN.md 4.2 목록), 편집 도움(포트 변경 영향 미리 보기, 프로그램이 쓰는 명령어 목록, 영향 경로 보기).
- **점검:** 4장과 11장을 다시 읽었다. 4장의 검사 목록은 모두 값이 정의되지 않았거나 구조상 동작할 수 없는 경우다. 11장에서 정오를 판단하던 항목은 11.9의 포트 통과 진단 하나였다. 11.13 제출 점검(진단 0건, 남은 Probe, 원조에서 열리는지)은 파일 상태 점검이라 둔다.

## D-020 참조 single-cycle MIPS 회로

- **날짜:** 2026-09-24
- **결정:** 참조 회로는 `tests/mips/ref-mips.circ`에 둔다(`tests/circ`는 기본 라이브러리만 쓰는 엔진 회귀 입력이라 분리). 원조 API로 생성하고 연결은 라벨 터널, 레지스터 파일은 main에 펼친다. 분기 가산기는 PC 기준(PC + imm×4)이다. 결과 비교는 원본 spim을 `-noexception`으로 불러 `run 0x00400000`으로 main부터 돌리고 `print_all_regs`·`print 주소`로 레지스터와 `.data`를 받는다. spim이 미리 채우는 `$a1`·`$a2`·`$gp`는 프로그램이 쓸 때만 비교한다.
- **이유:** 우리 테스트용 회로다(학생 설계 아님). 기계어가 QtSpim 그대로이므로 회로가 PC 기준으로 계산해야 SPIM과 같은 결과가 난다(사용자 지시). 예외 처리기를 켜고 spim을 돌리면 시작 코드가 `$a0~$a2`, `$ra`를 바꿔 조건이 달라지고, 끄고 `run 0x00400000`하면 회로와 같은 시작 조건이 된다. spim 명령줄에는 레지스터를 설정하는 명령이 없다.
- **Stack 깊이 기록:** 클럭 상승 에지의 접근만 센다. 전파 중 잠깐 나타나는 주소를 세면 깊이가 틀렸다(팩토리얼에서 8바이트 더 깊게 잡힘).
- **대안:** 서브회로로 나눈 학생식 회로(테스트가 레지스터 값을 읽기 어려움), 교재식 PC+4 분기 가산기(QtSpim 기계어와 결과가 달라짐).

## D-021 트랙 A 배포: Windows 빌드와 draft Release

- **결정:** `hcs-asm.exe`는 GitHub Actions Windows 러너에서 MSYS2 UCRT64의 MinGW g++로 정적 링크해 만든다(`LDFLAGS=-static`). Windows 작업은 hcs-asm 골든과 QtSpim GUI 출력 비교를 돌린다(원본 spim 오라클은 Linux만). `v*` 태그를 push하면 CI가 `tools/package-track-a.sh`로 `hcs-mips-<버전>-windows.zip`·`-linux.zip`(jar, hcs-asm, 사용안내, 라이선스)을 만들어 **draft** Release에 올린다. 사용 안내는 `docs/track-a-guide.md`다.
- **이유:** hcs-asm은 Qt가 필요 없는 작은 명령줄 도구라 MSVC·Qt 설정 없이 MinGW로 충분하다. SPIM 원본에도 MinGW 빌드 설정이 있다. 정적 링크면 학생 PC에 런타임 DLL이 없어도 된다. JSON은 Windows에서도 LF로 내도록 표준 출력을 바이너리 모드로 둔다. 학생 배포는 사용자 결정이라 draft로 둔다.
- **대안:** Hallym MIPS처럼 MSVC + winflexbison(Qt 없이도 가능하지만 설정이 길다), 크로스 컴파일(Windows에서 실제로 도는지 확인 못 함).

## D-024 .circ 확장 정보의 저장 형식과 앱 환경설정

- **날짜:** 2026-09-24(#67)
- **결정:** PLAN.md 7.0의 네임스페이스는 `<project>`의 마지막 자식 `<hcs:ext xmlns:hcs="urn:hallym-circuit-studio:ext" version="1">` 하나다. 그 안에 `<hcs:circuit name="…">`마다 항목 요소(`<hcs:tunnel …/>`처럼 종류 이름과 문자열 속성)를 둔다. 엔진의 XmlReader·XmlWriter는 바꾸지 않는다. 파일을 연 뒤 이 요소를 따로 읽어 LogisimFile 옆에 붙이고(`CircExtensions`), 원조 방식으로 저장한 파일 끝에 다시 넣는다(`ProjectActions`의 `// HCS:` 두 곳, proj 패키지라 엔진 밖). 확장 정보가 없으면 저장한 파일을 건드리지 않는다. 모르는 종류·속성은 그대로 두었다가 다시 쓴다. 사람마다 다른 설정은 .circ가 아니라 OS별 설정 폴더(Windows `%APPDATA%\HallymCircuitStudio`, macOS `~/Library/Application Support/HallymCircuitStudio`, 그 밖 `$XDG_CONFIG_HOME/hallym-circuit-studio`)의 `settings.properties`에 둔다. 포크가 더한 코드는 `app/src-hcs/`, 문구는 그 옆의 `messages(_ko).properties`다.
- **이유:** 원조 2.7.1의 XmlReader는 `<project>` 아래 모르는 요소를 건너뛴다(JDK 8에서 원조 jar로 확인, `CircExtensionTest`). 요소 하나에 모으면 원조로 다시 저장했을 때 빠지는 범위가 분명하다. 엔진 writer를 바꾸면 규칙 2.1의 패치가 되고, 확장 정보가 없는 파일의 바이트 호환(D-006)을 따로 증명해야 한다. 저장 뒤 끼워 넣기는 확장 정보가 없을 때 아무 일도 하지 않으므로 그 증명이 필요 없다.
- **대안:** 부품 속성으로 저장(원조가 모르는 속성은 경고 없이 버리지만 부품마다 흩어지고 회로 단위 정보를 둘 곳이 없음), .circ 옆 별도 파일(제출할 때 빠뜨림), 엔진 XmlWriter 패치(규칙 2.1).

## D-025 포크의 모양: FlatLaf Light + 디자인 토큰 + Pretendard

- **날짜:** 2026-09-24(#21)
- **결정:** 포크는 시작할 때(`Startup`, `// HCS:`) 시스템 모양 대신 FlatLaf Light에 `Tokens`(D-008, Hallym MIPS `tokens.h` 값)를 입히고, UI 글꼴을 번들한 Pretendard 13px로 둔다. 색 배치는 Hallym MIPS `light.qss`를 따른다. 선택은 옅은 파랑 바탕에 navy 글자, 기본 버튼은 blue, 툴팁은 navy, 스크롤바는 12px에 화살표가 없다. Pretendard를 못 쓰면 맑은 고딕 → Noto Sans CJK KR → Segoe UI 순으로 쓴다. 바뀌는 것은 Swing 부분(메뉴·트리·표·대화상자)뿐이고 캔버스 그림은 엔진 그대로다. `-tty`에서는 모양을 설치하지 않는다. 다크 모드는 넣지 않는다(Hallym MIPS도 라이트 전용이고, 다크는 대비 근거부터 새로 설계해야 한다). FlatLaf 3.7.2는 포크 jar에 넣고(`Multi-Release`), Apache-2.0 전문을 `META-INF/LICENSE-FlatLaf.txt`로 함께 넣는다.
- **이유:** 두 제품이 같은 학생에게 쓰이므로 색과 글꼴이 같아야 한다. 토큰을 Java 한 곳에 두고 FlatLaf 설정 값을 거기서 만들면 값이 어긋나지 않는다. `ThemeTest`가 글자·바탕 쌍의 WCAG AA(4.5:1)와 teal을 글자에 쓰지 않는 규칙을 확인한다.
- **라이선스:** Apache-2.0은 GPL 3과 호환되고 GPL 2와는 호환되지 않는다. Logisim은 "GPL 2 또는 그 이후"이므로 FlatLaf를 넣은 포크 jar는 GPL 3 조건으로 배포된다(NOTICE에 적음). 트랙 A의 `hcs-mips.jar`는 FlatLaf를 넣지 않으므로 그대로다.
- **대안:** 시스템 모양 유지(Windows·macOS·Linux에서 모양이 다르고 토큰을 입힐 수 없음), FlatLaf `.properties` 파일로 설정(토큰이 Java와 파일 두 곳에 생김), 다크 모드 동시 제공(대비 근거 없음).

## D-026 한국어 UI와 시작 안내

- **날짜:** 2026-09-24(#23)
- **결정:** 원조 문구 번들 16개 전부를 `resources/logisim/ko/`에 한국어로 옮기고 `settings.properties`의 locales에 `ko`를 더한다. 파일은 원조 번들처럼 ASCII(`\uXXXX`)로 저장한다. 언어는 원조와 같이 OS 언어를 따르고 환경설정 › 언어에서 바꾼다. 다음은 영어 그대로 둔다: 저장 파일에 들어가는 `newCircuitName`(main), 한국어 도움말이 없어 `helpsetUrl`, 부품 몸체에 그려지는 짧은 약어(en, ctr, sel, D, A 등)와 단위·형식 문자열, 부품 이름 RAM·ROM·LED·TTY. 창 제목의 제품 이름 "Logisim"은 이번에 바꾸지 않는다. 포크가 더한 문구는 `kr.ac.hallym.hcs.app.messages(_ko)`에 둔다. 첫 실행 때 시작 안내(카드 6장: 환영, 부품 놓기, 선 잇기, 값 바꾸기, MIPS 부품, 저장)를 한 번 띄우고 도움말 › 시작 안내에서 다시 연다. 캐릭터는 첫 장(인사)과 마지막 장(OK)에만 흰 바탕에 비율 그대로 160px로 둔다.
- **이유:** 학생 대부분이 한국어 OS를 쓴다. 저장 파일은 UI 언어와 무관해야 원조와 바이트 호환이 유지된다. `LocaleSaveCompatTest`가 기본 라이브러리 전 부품과 tests/circ 회로를 한국어 UI로 저장해 영어와 같음(ASCII만)을 확인하고, `KoreanBundleTest`가 키·자리표시자(`%s`, `%$1`)·끝 공백이 영어 번들과 같음을 확인한다. 부품 몸체의 약어는 교재 표기와 같고 자리가 좁아 번역하면 그림이 깨진다.
- **`-tty`:** 명령줄 `-locale`이 없으면 `-tty` 출력은 한국어 OS에서도 영어다. 원조 2.7.1은 한국어 번들이 없어 늘 영어로 냈고, 채점 스크립트가 그 출력(통계 머리, 멈춘 이유)을 읽을 수 있다. GUI에서 고른 언어 설정은 바꾸지 않는다(`TtyLocaleTest`). 테스트는 Java 환경설정을 빌드 폴더에 따로 두어 개발자 PC의 Logisim 설정(원조와 같은 저장소)을 바꾸지 않는다.
- **대안:** 포크 문구만 번역(메뉴·속성이 영어로 남아 학생이 두 언어를 오감), UTF-8 번들(원조 번들과 형식이 달라지고 JDK 8 방식 읽기에서 깨짐), 창 제목까지 제품 이름 변경(정보 창·로고 작업과 함께 따로 정한다).

## D-027 파일 탭은 겹쳐 둔 프로젝트 창으로

- **날짜:** 2026-09-24(#68)
- **결정:** 파일 탭은 Logisim의 "파일마다 창 하나" 구조를 그대로 두고, 열린 창들을 같은 자리·크기에 겹쳐 활성 탭의 창만 보이게 해서 만든다. 창마다 캔버스 위에 같은 탭 줄(`FileTabBar`)을 그리고, 탭 목록은 `TabModel` 하나(GUI 없이 테스트)다. 그 아래 줄은 이 파일에서 연 회로 탭과 시뮬레이션 경로(`main › datapath`, 앞 단계를 누르면 그 상태로 올라감)다. 저장 안 된 파일은 이름 앞 ●와 툴팁으로 알린다. 열린 파일 목록과 활성 탭은 앱 환경설정에 남겨, 명령줄에 파일이 없으면 다음 실행 때 다시 연다. File › 종료는 목록을 남기고, 탭을 하나씩 닫으면 목록에서 빠진다. Logisim의 리스너 목록은 약한 참조라 탭 코드가 붙이는 리스너는 모두 필드로 붙잡는다.
- **이유:** 되돌리기 기록, 시뮬레이션 상태, 창 메뉴, 저장 확인이 원래 프로젝트(창)마다 따로라 탭마다 따로가 그대로 된다. 한 창에 여러 프로젝트를 넣으려면 Frame·메뉴·툴바·캔버스 연결을 다시 짜야 하고, 4b의 창 분리는 이 구조에서 "그 창만 겹치기에서 빼기"로 끝난다.
- **대안:** 한 JFrame 안에 프로젝트별 패널을 CardLayout으로 두기(Frame 전체 재구성, 메뉴·단축키가 프로젝트마다 묶여 있어 원본 수정이 큼), 탭 없이 창 메뉴만 쓰기(요구사항 11.1을 못 채움).

## D-028 확대 단축키 Ctrl+0·Ctrl+1과 도구 선택

- **날짜:** 2026-09-24(#69)
- **결정:** PLAN.md 11.2대로 Ctrl+0은 전체 맞춤, Ctrl+1은 100%다. 원조 2.7.1은 Ctrl+0~9로 도구 모음의 도구를 고르는데, 포크는 Ctrl+2~9만 도구 선택으로 남긴다(`KeyboardToolSelection`, `// HCS:`). 확대 단계는 25·33·50·67·75·100·125·150·200·250·300·400%이고, 상태 표시줄의 배율 칸과 Ctrl+휠·Ctrl+= / Ctrl+-가 같은 단계를 쓴다. Ctrl+휠은 커서 아래 점을 고정하고, 스페이스+끌기·가운데 버튼 끌기로 이동한다(라벨을 입력하는 텍스트 도구에서는 스페이스가 공백이다). F는 캔버스에 초점이 있을 때 선택 부분에 맞춘다. 배율은 원조처럼 앱 환경설정에만 두고 .circ에는 저장하지 않는다.
- **이유:** 사용자가 정한 명세다. 원조의 Ctrl+1(첫 도구) 습관은 도구 모음 클릭이나 Ctrl+2~9로 대신할 수 있고, 4b의 단축키 설정에서 바꿀 수 있게 한다.
- **대안:** 확대에 다른 키(Ctrl+Shift+0 등)를 쓰기(명세와 다름), 원조 도구 단축키를 그대로 두고 충돌 허용(어느 쪽이 먼저 받을지 Swing 등록 순서에 따라 달라짐).

## D-029 자동 저장과 복구

- **날짜:** 2026-09-24(#70)
- **결정:** 저장 안 된 변경이 있는 열린 파일을 2분마다(`autosave.minutes`) 앱 설정 폴더 `autosave/`에 `<이름>-<경로 해시>.circ`와 원래 경로·시각 기록으로 저장한다. 원본 .circ와 그 폴더에는 아무것도 쓰지 않는다. 내용은 원조 writer(`LogisimFile.write`, 패키지 전용)를 리플렉션으로 불러 쓰고, 라이브러리 상대 경로는 원래 폴더 기준 절대 경로로 바꾸며, 사용자 확장 정보(hcs:ext)도 넣는다. 정상 저장하거나 탭을 닫으면 그 자동 저장을 지운다. 다음 실행 때 남은 자동 저장이 있으면 복구를 제안하고, 복구한 창은 "이름 (복구됨)" 탭으로 열리며 저장하면 원래 파일 위치를 미리 고른 저장 창이 뜬다. 창에 .circ를 끌어 놓으면 연다. 최근 파일 목록은 원조의 파일 › 최근 파일 열기를 그대로 쓴다.
- **이유:** `Loader.save`는 열린 파일의 이름과 저장 위치를 바꾸므로 자동 저장에 쓸 수 없다. 엔진 writer를 바꾸지 않고 그대로 부르면 저장 결과가 정상 저장과 같다(`AutoSaveStoreTest`가 원본 해시 불변과 D-006 동등을 확인). 복구한 창이 자동 저장 폴더를 제 위치로 알고 저장하면 학생이 파일을 잃으므로 저장 위치를 묻는다.
- **대안:** .circ 옆 `~` 백업 파일(학생 폴더에 파일을 만듦), 엔진 writer에 경로 인자를 더하는 패치(규칙 2.1).
- **보강(검토):** 복구한 창은 자동 저장 폴더에서 열렸으므로, 원조 `Loader.save`가 새 위치를 정하기 전에 라이브러리 경로를 그 폴더 기준(절대 경로)으로 쓴다. 복구한 창의 저장은 한 번 저장해 위치를 정한 뒤 다시 저장해 원래 폴더 기준 상대 경로로 쓴다(`saveRecovered`, 정상 저장과 D-006 동등을 테스트). 원조의 최근 파일 목록에 들어간 자동 저장 경로는 원래 파일 경로로 바꾼다.

## D-030 공용 식별자와 부품 종류 등록표

- **날짜:** 2026-09-24(#24)
- **결정:** 부품 이름은 라벨이 있으면 라벨, 서브회로는 회로 이름 + 번호, 그 밖은 등록표의 짧은 이름 + 번호(`AND #3`)다. 번호는 같은 종류끼리 위→아래, 왼쪽→오른쪽 순서로 1부터 매긴다. 경로는 `main › datapath › PC`, 포트는 `PC.Q`로 적는다. 짧은 이름과 포트 이름은 번역하지 않는다. 등록표(`Kinds`)의 키는 부품의 저장 이름(.circ의 `name`)이고, 분류·상태 보유 여부(연결 탐색이 멈추는 곳)·포트 이름 규칙·빠른 속성을 한 곳에 둔다. 포트 이름은 원조 소스의 포트 순서를 따르고, 선택기류처럼 속성에 따라 포트가 바뀌는 부품은 속성을 읽어 정한다. 서브회로 포트 이름은 안쪽 핀 라벨이다. MIPS 부품 포트는 PLAN.md 7.0의 Verilog 모듈 포트 이름과 같다.
- **이유:** 진단·마우스 오버·찾기·향후 Verilog 이름이 같은 규칙을 써야 한다. 파일 안 부품 순서는 원조가 저장할 때마다 달라지므로(D-006) 번호는 위치로 정한다. UI 언어가 바뀌어도 경로가 같아야 진단 기록과 테스트가 흔들리지 않는다.
- **대안:** 원조의 표시 이름 사용(번역되어 언어마다 달라짐), 파일 안 순서로 번호(저장할 때마다 바뀜).

## D-031 연결 탐색 엔진(넷 모델)

- **날짜:** 2026-09-24(#71)
- **결정:** 넷은 원조의 연결 계산(`Circuit.getWireSet`)으로 묶은 선들과, 그 선의 끝점이나 선 위에 닿은 포트, 선 없이 같은 점에 닿은 포트로 만든다. 같은 이름의 터널은 한 넷으로 합친다. 스플리터는 넷을 합치지 않고 `bitN` 속성으로 비트 대응을 둔다. 서브회로는 원조 `SubcircuitFactory`의 포트 순서(`getPortOffsets`)로 안쪽 핀과 바깥 포트를 잇는다. 탐색(`Trace`)은 앞(읽는 포트 → 그 부품의 출력)·뒤(구동 포트 → 그 부품의 입력)로 가고, 등록표에서 상태를 가진 부품(레지스터·메모리 등)에서 멈추며 옵션으로 넘는다. 영향 경로(2c), E·X 추적(4), 넷 정보·마우스 오버(2b)가 이 하나를 쓴다.
- **이유:** 부록 A.4의 연결 규칙(끝점 없는 교차, 한쪽만 잘린 교차, 두 선 모두 잘린 교차, T자, 포트 위를 지나는 선)을 따로 구현하면 원조와 어긋날 수 있다. 원조의 계산을 그대로 쓰고, 규칙마다 원조 엔진(`-tty`)의 결과와 넷 모델이 같은지 `NetlistTest`가 확인한다.
- **대안:** 선분 기하로 직접 계산(규칙을 다시 구현해야 함), 시뮬레이션 값으로 넷 추정(값이 같다고 같은 넷은 아님).

## D-032 스플리터 편집기와 대상별 우클릭 메뉴의 자리

- **날짜:** 2026-09-25(#105)
- **결정:** 우클릭 메뉴는 원조 Menu Tool(tools 패키지, 엔진 밖)이 만든 메뉴 뒤에 대상별 항목을 덧붙인다(`ContextMenus`, `// HCS:` 한 곳). 우클릭이 Menu Tool로 가는 것은 .circ의 `<mappings>` 그대로다. 스플리터는 "스플리터 편집…", 여러 비트 선은 "비트 나누기…"·"비트 하나 뽑기 [n]", 선을 여러 개 고르면 "하나의 버스로 합치기"가 붙는다. 편집 결과는 원조 표준 속성(fanout, incoming, bitN)으로만 바꾸고 원조 `CircuitMutation`으로 만들어 되돌리기 한 번으로 취소된다. 팔 이름은 `<hcs:splitter x y arm0 …>` 확장 항목(D-024)에 스플리터 위치로 두고, 이름이 없으면 항목을 지운다. 합치기는 고른 순서(선택이 바뀔 때마다 기록한 순서, 먼저 고른 선이 위 = MSB)와 각 선의 폭만 쓰고, 새 스플리터를 고른 선들 오른쪽에 두며 연결은 학생이 한다. 캔버스 위 팔 라벨(`[31:26] op` 칩)은 라벨 칩 체계와 함께 #79에서 그린다.
- **이유:** 스플리터 그림과 속성 편집은 엔진(circuit 패키지) 코드라 바꾸지 않는다. 메뉴를 Menu Tool 뒤에 붙이면 원조 항목(삭제, 속성 보기, 오름·내림차순 나누기)이 그대로 남는다. 합치기에서 도구가 선을 이으면 선 배치를 도구가 정하게 되므로(1장 원칙) 만들기만 한다. 위치로 이름을 두는 것은 원조 부품에 고유 ID가 없기 때문이다(스플리터를 옮기면 이름이 떨어진다).
- **대안:** 스플리터 부품을 새로 만들기(원조에서 열리지 않음), 이름을 라벨 속성에 넣기(원조 스플리터에는 라벨 속성이 없음).
- **보강(검토):** 합치기는 팔 이름을 채우지 않는다(학생이 직접 지정한 정보만 저장, 11.0). 팔 이름 바꾸기는 회로 변경과 같은 되돌리기 한 단계에 넣고, 저장할 때 그 위치에 팔 수가 같은 스플리터가 없는 이름 항목은 지운다(되돌리기·삭제·이동 뒤에 남지 않게). 사각형으로 여러 선을 한꺼번에 고르면 순서를 알 수 없으므로 합치기를 끄고 Shift+클릭으로 하나씩 고르라고 안내한다(도구가 순서를 정하지 않음). 폭을 모르는 선이 있으면 합치기를 끈다.

## D-033 대상별 우클릭 메뉴의 항목

- **날짜:** 2026-09-25(#72, #73)
- **결정:** D-032의 틀(원조 Menu Tool 메뉴 뒤에 붙이기)에 대상별 항목을 둔다. 포트: 핀·상수(입력만)·프로브·터널 붙이기(연결점이 포트와 같은 점, 몸체는 부품 바깥쪽, 폭은 포트 폭, 라벨은 포트 이름), 게이트 입력 부정. 핀: 입력·출력 바꾸기, 폭, 3상태, 풀, 라벨. 빈 곳: 붙여넣기, 화면에 맞추기. 여러 부품: 공통 속성(방향·폭) 한 번에 바꾸기, 라벨 일괄 편집. 게이트: 입력 수, 크기, 방향, 폭, 종류 바꾸기, 라벨, 복제. 선: 넷 정보(값을 내는 포트·읽는 포트·그 밖, 공용 식별자 이름), 넷 전체 선택, 선을 터널로 바꾸기. 서브회로: 모양 편집(들어가기는 원조 항목 "View"). 터널: 다음 같은 이름 터널로 이동, 모두 선택. 모든 항목은 원조 부품·속성만 바꾸고 원조 `CircuitMutation` 하나라 되돌리기 한 번이다. 게이트 종류 바꾸기는 입력 핀 자리를 그대로 두도록 부품을 옮기고, 출력 자리가 바뀌면 출력에 닿은 선을 늘이거나 줄인다(그런 선이 없으면 짧은 선을 더한다). 공용 식별자는 라벨로 이름이 붙는 포트 하나짜리 부품(핀·터널)을 한 번만 쓴다(`d.d` 대신 `d`). 사이클 뷰 추가(3단계)와 영향 경로(2c)는 그 단계에서 붙인다.
- **이유:** 부록 A.5처럼 NAND·NOR·XOR·XNOR는 입력 핀이 10px씩 멀어, 종류만 바꾸면 입력 선이 끊긴다. 종류 쌍 30 × 입력 수 3 × 크기 3 × 방향 4 = 1080가지에서 연결이 그대로인지 넷 모델로 확인한다(`CircuitEditsTest`).
- **대안:** 출력 자리를 고정하고 입력 선을 모두 다시 긋기(입력 수만큼 선을 고쳐야 하고 학생 배선이 바뀜).

## D-034 빠른 프로브의 자리

- **날짜:** 2026-09-25(#75)
- **결정:** 선 우클릭 "프로브 붙이기"(16진·10진 부호 있음·10진 부호 없음·2진)와 선 위에서 P(여러 비트는 16진, 1비트는 2진)는 원조 Probe와 짧은 선을 더한다. 자리는 누른 곳에서 가까운 선 위 격자점 p부터 찾고, p에서 선과 수직으로 20~50px 떨어진 q에 프로브를 둔다. p에 다른 넷의 선·포트가 있으면 안 되고, p–q 사이와 q에는 어떤 선(교차 포함)·포트·부품도 없어야 하며, 프로브 몸체 자리도 비어 있어야 한다. 자리가 없으면 붙이지 않고 알린다. 라벨은 넷의 터널·핀 이름이다. "세 진법 모두"는 Hallym MIPS 라이브러리의 Radix Probe가 있는 파일에서 3단계 관찰 기능과 함께 붙인다. 빈 곳 우클릭에 모든 프로브 선택·삭제가 있다(원조 Probe에는 숨김 속성이 없어 숨기기는 두지 않는다).
- **이유:** 부록 A.4에서 선 끝점이 다른 선 중간에 닿거나 선이 남의 포트 위를 지나면 연결된다. 규칙을 모두 피해야 프로브가 넷을 합치거나 끊지 않는다(`QuickProbeTest`가 넷 모양 불변을 확인).
- **보강(#69):** 캔버스는 마우스 좌표를 배율로 나눠 넘기므로(원조 `Canvas.zoomEvent`) 확대 중 끌어 이동하는 양은 화면 좌표로 잰다.
- **보강(검토):** "모든 프로브 삭제"는 프로브 연결점에서 다른 것이 닿지 않는 막다른 선도 함께 지운다(빠른 프로브의 짧은 선, 또는 학생이 프로브에만 이은 선). 그 선은 프로브에만 이어져 있어 넷은 바뀌지 않는다.

## D-035 조작과 단축키

## D-036 찾기와 터널 이름 목록

- **날짜:** 2026-09-25(#80)
- **결정:** Ctrl+F는 라벨·터널 이름·서브회로 이름을 주 회로에서 서브회로 부품을 따라 내려가며 모두 모은 색인에서 찾는다(대소문자 무시, 이름이 정확히 같은 것 먼저). 같은 서브회로를 두 번 쓰면 경로가 둘(`main › alu #1 › PC`, `main › alu #2 › PC`)이고, 주 회로에서 닿지 않는 회로도 제 이름을 경로로 넣는다. 고르면 그 인스턴스의 시뮬레이션 상태로 들어가(원조 `SubcircuitFactory.getSubstate`) 부품을 선택하고 보이는 곳으로 옮긴다. 같은 창의 터널 탭은 지금 회로의 터널 이름과 개수를 보이고 고르면 같은 이름 터널을 모두 선택한다. 같은 이름 터널로 이동·모두 선택은 터널 우클릭(D-033)에도 있다.
- **이유:** 서브회로 안 레지스터를 찾을 때 편집 화면이 아니라 그 인스턴스의 값이 보여야 한다. 이름과 경로는 공용 식별자 규칙(D-030)이라 진단·마우스 오버와 같다.
- **대안:** 편집 화면(회로 정의)으로만 가기(인스턴스마다 다른 값을 볼 수 없음).

- **보강(2026-09-25, #135):** 찾기 결과는 종류·글자·경로가 같은 항목을 한 줄로 묶어 개수와 함께 보인다(예: "pc 터널 · main › pc (7곳 · 누르면 펼침)"). 누르면 위치별 줄("위치 (100, 200)", 위→아래·왼쪽→오른쪽 순)로 펼친다. 두 번 누르면 그 위치로 간다. 경로가 다르면(다른 서브회로 인스턴스) 따로 줄이다(`NameIndex.group`).

## D-039 빠른 속성 창, 오른쪽 속성 패널, 라벨 제자리 편집

- **날짜:** 2026-09-25(#74)
- **결정:** 선택·편집 도구로 같은 종류 부품을 고르면 그 위(자리가 없으면 아래)에 빠른 속성 창이 뜬다. 보일 속성은 부품 종류 등록표(`Kinds.quickAttrs`, D-030)에서 최대 5개를 읽는다. 목록 속성의 선택지는 원조 속성 편집기의 목록에서 읽고, 글자 속성은 제자리 칸에서 고친다. "모든 속성"은 오른쪽 속성 패널을 편다. 아래 줄은 원조 2.7.1의 숨은 단축키를 보인다. 숨은 단축키는 부품의 원조 `KeyConfigurator`에 숫자 키와 Alt+숫자 키를 넣어 보고 알아낸다(예: AND는 숫자=입력 수, Alt+숫자=데이터 비트). 여기에 우리 R(돌리기)과 F2(라벨)를 더한다. 원조 방향키 방향 바꾸기는 D-035의 한 칸 옮기기에 자리를 내줬으므로 적지 않는다. 라벨은 F2나 부품 더블클릭으로 부품 자리에서 고친다. 입력 핀 더블클릭은 D-035의 값 넣기 그대로다. 바꾸기는 모두 원조 속성 표(`AttrTableSelectionModel`)와 같은 `SetAttributeAction`이다. 이름도 같고, 되돌리기는 한 번이며, 값이 그대로면 Action을 만들지 않는다. 원조 속성 표는 왼쪽 아래에서 캔버스 오른쪽 도킹 패널로 옮기고 접을 수 있게 한다. 배율 조절은 탐색 창 아래에 남긴다. 패널 폭, 접힘, 빠른 속성 창 켜기는 앱 환경설정에 둔다.
- **이유:** 사용자가 정한 명세(11.4)다. 선택지와 단축키를 원조에서 읽으면 표시와 실제 동작이 어긋나지 않는다. 같은 Action을 쓰면 되돌리기와 저장 결과가 속성 표로 고친 것과 같다(.circ 불변).
- **대안:** 선택지와 단축키 표를 손으로 적기(원조와 어긋날 수 있음), 도크를 창 전체 높이로 두기(도구 모음이 좁아져 잘림).

## D-040 라벨 칩·밀도, 터널 자동 색, 서브회로 상자 표시, 마우스 오버 정보

- **날짜:** 2026-09-25(#79)
- **결정:**
  - **라벨 칩.** 편집 캔버스에서 원조 라벨 글자 대신 칩을 그린다. 칩은 옅은 배경에 Pretendard를 쓰고, 글자는 회로 좌표 11px이며 화면에서 최소 10px이다. 칩은 원래 라벨 자리 가운데에 두고, 다른 칩이나 부품과 겹치면 위·아래·오른쪽·왼쪽, 그다음 대각선 순으로 한 걸음씩 옮긴다. 멀리 옮긴 칩은 지시선으로 잇는다(`LabelLayout`, 입력 순서와 무관한 결과).
  - **원조 라벨 빼기.** 원조 라벨은 엔진을 고치지 않고 gui 층에서 뺀다. 캔버스 그리기(`CanvasPainter`)가 원조 회로 그리기에 넘기는 Graphics를 감싸, 원조 라벨 `drawString`만 뺀다. 빼는 호출은 글자와 기준선 좌표가 원조 `TextField.draw`와 같은 식으로 계산한 값과 정확히 같은 것뿐이다. 라벨 값은 부품의 공개 기능 `TextEditable`(`InstanceTextField`)이 가진 `TextField`의 공개 값에서 읽는다. 그 필드 하나는 읽기 전용 리플렉션으로 꺼낸다.
  - **칩을 쓰지 않는 곳.** 터널은 이름이 곧 몸체라 원조 그대로 둔다. 인쇄와 그림 내보내기는 원조 그리기를 그대로 쓴다.
  - **밀도.** 밀도는 3단계(전부 / 핀·터널·서브회로만 / 마우스를 올린 것만)이고 앱 환경설정에 둔다. 상태 표시줄 단추로 바꾼다.
  - **버스 이름.** 이름 있는 넷(터널·핀 라벨, D-034 규칙) 중 폭이 2 이상이고 가장 긴 선이 60px 이상이면 칩으로 `이름[w-1:0]`을 붙인다.
  - **터널 자동 색.** 터널에는 이름의 FNV-1a 해시로 Okabe–Ito 팔레트(노랑 제외 7색)에서 고른 옅은 색을 칠한다. 저장하지 않고, 이름 글자는 그대로 보인다.
  - **서브회로 상자.** 원조 기본 모양 서브회로 상자 안에 포트 이름(안쪽 핀 라벨)을 7px로 적는다. 회로 이름은 칩 배치에 든 캡션으로 상자 아래(아래 변에 포트가 있으면 위)에 둔다. 원조 기본 상자는 폭이 30px 안팎이라 이름이 상자에 들어가지 않기 때문이다. 학생이 그린 모양은 건드리지 않는다.
  - **마우스 오버.** 부품 위에서는 전체 경로(`main › alu #1 › AND #3`, D-030), 라벨, 입력 수, 폭, 이름 있는 넷에 닿은 포트를 보인다. 선 위에서는 폭과 넷 이름을 보인다. 포트 위 툴팁(D-035)이 먼저다.
- **이유:**
  - 사용자가 정한 명세(11.12)다.
  - 원조 라벨을 그대로 두면 칩과 글자가 겹쳐 두 번 보이고, 겹침을 피해 칩을 옮길 수 없다.
  - 엔진 패키지 패치(`InstanceTextField`에 숨김 스위치) 대신 gui 층의 그리기 필터를 골랐다. 엔진 파일이 원본 그대로이기 때문이다. 필터가 빼는 것은 라벨 자리와 글자가 정확히 같은 호출뿐이다. 테스트는 걸러 낸 그림이 라벨 자리 밖에서 원조와 픽셀까지 같음을 확인한다(`LabelsTest`).
- **대안:**
  - `InstanceTextField` 최소 패치: 엔진 파일이 바뀌고 허용 목록에 한 줄이 늘어난다.
  - 칩을 원래 라벨 위에 덮기만 하기: 옮길 수 없어 겹침이 남는다.
  - 회로 이름을 상자 안에 억지로 줄여 넣기: 기본 상자에서는 읽을 수 없다.
- **보강(2026-09-25, 검토 반영):**
  - 처음 방식은 글자와 기준선 좌표만으로 걸렀다. 터널·글자 부품처럼 Graphics를 옮긴 뒤 상대 좌표로 글자를 그리는 부품이 있으면, 그 상대 좌표가 다른 부품 라벨의 절대 좌표와 우연히 같을 때 그 글자까지 빠질 수 있었다.
  - 그래서 부품 식별로 거르도록 바꿨다. 원조 `Circuit.draw`는 선용 Graphics 하나를 만든 뒤, 가려지지 않은 부품마다 `getNonWires()` 순서대로 `create()`를 한 번씩 부른다. 맨 위 필터는 이 순서로 자식 Graphics에 부품을 붙인다. 자식은 그 부품 자신의 라벨(글자·좌표)만 뺀다.
  - 순서가 어긋나면 라벨이 원조대로 남을 뿐이다.
  - `LabelFilterTest`가 원조와 거른 그리기의 drawString 호출을 전부 기록해 비교한다. 다룬 경우는 다음과 같고, 빠지는 것이 라벨 부품 자신의 라벨뿐임을 확인한다.
    - 같은 글자 "A"의 핀·출력 핀·레지스터·게이트 라벨, 터널, 글자 부품이 함께 있음
    - 같은 자리에 겹친 두 핀
    - 터널 글자와 좌표까지 같은 라벨
    - 확대 0.5·1·1.5·2배
    - 끌고 있는(가려진) 부품

- **보강(2026-09-25, 스플리터 팔 라벨):** PLAN 11.11의 "팔 라벨"(작은 표시 대신 `[31:26] op`)이 캔버스에 빠져 있었다. 이제 스플리터 팔 끝 옆에 범위를 적고, 이름이 있으면 이름도 붙인다(팔 이름은 D-032의 .circ 확장 정보). 가로로 뻗는 팔은 선 위에, 세로로 뻗는 팔은 오른쪽에 7px로 적는다. 밀도 "전부"이거나 마우스를 올린 스플리터일 때만 그리고, 저장하지 않는다(`LabelsTest.splitterArmLabelsShowRangesAndNames`).

## D-041 다시 실행(redo)

- **날짜:** 2026-09-25(검토 반영, 4b "되돌리기 목록" #92와 연결)
- **결정:** 원조 2.7.1에는 되돌리기만 있다. 다시 실행은 엔진과 원조 되돌리기 기록(`Project`의 undoLog)을 바꾸지 않고 프로젝트 사건을 듣는 `RedoStack`으로 만든다.
  - **쌓기:** 되돌린 동작(UNDO_COMPLETE)을 그때의 시뮬레이션 상태와 함께 쌓는다(최대 64개, 원조 되돌리기 기록과 같은 길이).

## D-044 화면 구성 정리(스크린샷 검토 1차)

- **날짜:** 2026-09-25
- **결정:**
  - **원조 도구 모음(조작·편집·텍스트·핀·게이트 아이콘 줄):** 레이아웃 편집 화면에서 숨긴다. .circ의 `<toolbar>`는 그대로 읽고 저장한다. 원조 Ctrl+2…9(그 목록의 도구 고르기)는 창의 루트에 다시 달아 그대로 동작한다(`ToolKeys`). 모양 편집 화면에서는 원조 도구 모음이 도형 도구(사각형·글자 등)라서 새 도구 모음 아래에 보인다.
  - **새 도구 모음:** 창 전체 폭(왼쪽 패널 위 포함)으로 올렸다. 위쪽 줄은 메뉴·도구 모음·파일 탭·회로 탭 넷이다. 원조 도구 모음에만 있던 텍스트 도구를 새 도구 모음에 옮겼다. 부품(게이트·출력 핀 등)은 부품 트리, 트리 검색, Ctrl+K로 고른다.
  - **탐색 창 위 아이콘 줄 두 개:** 도구 상자/시뮬레이션 트리, 레이아웃/모양 편집, 회로 추가·위아래·삭제 줄을 없앴다. 모두 원조 프로젝트 메뉴에 같은 항목이 있고, 서브회로 모양 편집은 우클릭에도 있다.
  - **부품 트리 위 검색창(명세 F):** 명령 팔레트와 같은 검색 모델(`Palette.search`)을 쓴다. 입력하는 동안 트리 자리에 부품·서브회로 목록을 보이고(명령은 빼고), 고르면 원조 도구를 고른다. 뒤 숫자(`mux 32`)는 도구 속성에 넣는다.
  - **배율:** 왼쪽 아래 옛 배율 칸을 없애고 창 전체 폭 상태 표시줄의 배율 단추 하나로 했다. 누르면 단계, 화면 맞춤, 격자 보이기를 고른다. 이 단추는 편집 화면의 원조 배율 모델을 직접 듣는다. 02b에서 옛 칸 25%, 상태 표시줄 100%로 어긋난 원인은 상태 표시줄이 시뮬레이션 사건 때만 배율을 다시 읽은 데 있었다(`ZoomStatusTest`).
  - **따라오는 결과:**
    - 원조 환경설정의 "도구 모음 위치"(`AppPreferences.TOOLBAR_PLACEMENT`)는 레이아웃 화면에서 효과가 없다. 새 도구 모음은 늘 위에 있다.
    - 트리 검색의 뒤 숫자는 원조 `ToolAttributeAction`으로 도구 속성에 넣는다. 원조 속성 표로 도구 속성을 바꿀 때와 같아서 되돌릴 수 있다. 원조처럼 기본값과 다르면 .circ의 `<lib>` 안 `<tool>`에 저장되고 파일이 "바뀜"이 된다.
- **이유:** 원격 스크린샷 검토 결과다. 같은 기능이 두 곳에 있어 위쪽 줄이 많았다.
- **대안:** 원조 도구 모음을 새 도구 모음 옆에 두기. 줄 수는 줄지만 같은 기능이 겹친다.

## D-045 캔버스 겹침 정리(스크린샷 검토 1차)

- **날짜:** 2026-09-25
- **결정:**

    - 포트 이름은 원조 `drawPort(i, label, dir)` 대신 포트가 놓인 변에서 14px 안쪽에 9px로 적는다.

  - MIPS 부품을 키워 여백 확보: 포트 위치가 바뀌어 기존 회로 연결이 깨진다.
  - 스택 깊이를 $sp 포트로 재기: 부품에 $sp 입력이 없다.

## D-050 Stack 몸체는 사용한 영역(최고 수위)만 보인다(스크린샷 검토 2차 B)

- **날짜:** 2026-09-25
- **결정:**
  - Stack 부품 몸체의 사용량 줄은 `used N B (peak)` 하나다. 기준(#134: SPIM 시작 `$sp` `0x7FFFEFFC`, 아니면 영역 맨 위)에서 접근한 가장 낮은 주소까지다. 팝해도 줄지 않는다.
  - "현재 깊이"는 보이지 않는다. Stack 부품은 `$sp`를 모른다. 마지막 접근 주소는 `$sp`가 아니다. `$sp`보다 위 칸을 읽을 수도 있고(`lw $ra, 4($sp)`), 한 번 푸시할 때 여러 칸을 쓸 수도 있다.
  - 현재 `$sp`와 깊이는 3단계 레지스터 패널이 "레지스터 파일로 표시"한 서브회로의 `$29`로 보인다(PLAN.md 5.1·5.3·6.2 수정).
  - 스크린샷 실행기는 .s 실행 장면에서 `halt` 출력 핀이 1이 되면 클럭을 멈춘다.
- **56 B와 480 B가 다른 이유:** 1차 스크린샷 11f는 480 B였다.
  - 원인은 실행기다. 재귀 factorial(fact(6))은 88 사이클에서 exit(syscall 10)하고, 그때 사용한 영역은 56 B(7단계 × 8 B)다. `RefMipsTest`가 확인하는 값과 같다.
  - 실행기는 멈추지 않고 45 + 400 사이클을 돌렸다. 참조 CPU는 syscall 10 뒤에도 PC를 계속 올리므로 main 뒤에 있는 `fact`를 `$a0 = 720`으로 다시 실행했다. 그 재귀가 Stack을 계속 키워 480 B를 찍었다.
  - 도구의 계산은 맞았고, 장면이 exit 뒤 상태였다.
- **이유:** 검토에서 "현재 깊이"가 `$sp`처럼 보였지만 실제로는 마지막 접근 주소라 틀릴 수 있었다. 부품이 모르는 것은 보이지 않는다(PLAN.md 1장, 사실만 알린다).
- **대안:** Stack에 `$sp` 입력 포트를 더하기. 포트 이름·배선이 과제 회로와 달라지고, 원조 2.7.1용 부품의 모양도 바뀐다.

## D-052 정적 진단 엔진의 판정 규칙(2c, #25·#26)

- **날짜:** 2026-09-25
- **결정:** `kr.ac.hallym.hcs.app.diag.StaticCheck`가 회로 모델만 보고(GUI 없이) PLAN.md 4.2의 정적 검사 7가지를 한다. 회로 정의마다 한 번 돌고, 인스턴스가 여럿이어도 원인은 한 곳이다.
  - **값이 있는가:** 비트 단위로 본다. 넷의 비트를 마디로 두고, 스플리터가 잇는 비트끼리 묶는다(union-find). 출력 전용 포트, 풀 저항, 스플리터·터널이 아닌 양방향 포트가 닿은 마디가 "값 있음"이다. 포트는 한 비트라도 값이 있으면 연결된 것으로 본다. 일부 비트만 빈 경우는 동적 진단(4단계) 몫이다.
  - **클럭 미연결:** Register, Counter, 플립플롭, Random의 clk가 비었을 때 알린다. Data Memory·Stack은 MemWrite가 쓰일 때, Console은 Syscall이 쓰일 때만 알린다(읽기만 하면 클럭이 없어도 동작한다).
  - **합선:** 한 넷에 출력 전용 포트가 둘 이상일 때 알린다. 출력이 떠 있을 수 있는 부품은 세지 않는다: Controlled Buffer·Inverter, RAM, ROM, Instruction Memory·Data Memory·Stack(PLAN.md 6.2의 ReadData 공유), 3상태 핀·디먹스·디코더, enable을 켠 plexer.
  - **폭 불일치:** 원조 계산(`Circuit.getWidthIncompatibilityData`)을 그대로 쓰고, 그 점의 포트 이름과 폭을 말한다.
  - **연결 안 된 입력:** 비면 동작할 수 없는 입력만 알린다. 대상은 Register D, 산술 a·b, Mux·Decoder select, Instruction·Data Memory·Stack Addr 등이고, 등록표는 `REQUIRED`다. 게이트는 입력이 하나도 없는데 출력이 쓰일 때만 알린다. 원조는 게이트의 빈 입력을 무시하고 2.7.1 게이트 기본 입력 수는 5개라, 쓰지 않는 입력을 알리면 정상 회로에서 메시지가 쏟아진다.
  - **끊긴 선:** 값이 없는 넷에 선이나 다른 포트가 닿아 있고 입력이 그 넷을 읽으면 알린다. 아무것도 닿지 않은 선택 입력은 원조가 기본값으로 두므로 알리지 않는다.
  - **짝 없는 터널:** 받는 쪽만 알린다. 이름이 하나뿐인 터널 중, 넷에 값이 없고 입력으로 이어지는 것이다. 비슷한 이름(대소문자만 다르거나 편집 거리 2 이하, 짧은 이름은 1)을 함께 적는다. 보내기만 하는 터널이나 이름만 붙인 터널(참조 CPU의 쓰지 않는 스플리터 팔 등)은 동작을 막지 않으므로 알리지 않는다. 짝 없는 터널이 원인인 입력·클럭은 터널 하나로만 말한다(원인 한 곳).
  - **서브회로 포트 미연결:** 인스턴스의 입력 포트에 값이 없을 때 알린다. 쓰지 않는 출력은 알리지 않는다.
  - **조합 루프:** 비트 마디 그래프에서 강하게 연결된 묶음(반복형 Tarjan)을 찾는다. 게이트·plexer·산술·Bit Extender는 입력 → 출력으로 잇는다. 서브회로는 안쪽 입력 핀 → 출력 핀 도달을 재귀로 요약해 잇는다. 클럭으로 기억하는 부품은 루프를 끊는다.
- **보강(2026-09-25, 2c 검토 반영): 게이트 빈 입력과 프로젝트 옵션 `gateUndefined`.**
  - 원조는 Project › Options › Simulation의 "Gate Output When Undefined"를 .circ에 저장한다.
  - `ignore`(기본)이면 빈 게이트 입력을 무시하므로 알리지 않는다(위 규칙 그대로).
  - `error`이면 빈 입력 하나만 있어도 게이트 출력이 E가 된다. 그래서 출력이 쓰이는 게이트의 빈 입력을 모두 한 메시지로 알린다(예: `main › AND #1의 입력 in2, in3, in4이(가) 연결되지 않았습니다.`). 원인 한 곳은 그 게이트다.
  - 테스트: 같은 5입력 AND 회로를 두 설정으로 확인한다. `error`로 저장했다가 다시 연 .circ(rules_test_v2와 같은 경우)도 확인한다.
- **테스트(#26):**
  - 정상 회로(엔진 회귀 4개, 데모, 참조 CPU)는 0건이다. 엔진 회귀의 `values.circ`는 일부러 E·x를 만드는 회로라, 그 두 원인(합선, 떠 있는 터널)만 나온다.
  - 고장 회로 10개는 각각 원인 한 곳이 이름과 함께 나온다. 서브회로를 지나는 루프는 잡고, 레지스터를 지나는 되먹임은 루프로 보지 않는다.
- **이유:** PLAN.md 4.4(원인 한 곳, 학생이 붙인 이름)와 "정상 회로 0건"을 함께 지키려면, 원조가 조용히 허용하는 경우(빈 게이트 입력, 떠 있는 출력 공유, 이름만 붙인 터널)를 빼야 한다.
- **대안:** 모든 빈 입력 알리기. 원조 기본 5입력 게이트 때문에 정상 회로가 경고로 덮인다.

## D-055 따라오는 배선과 선분 평행 이동의 안전 기준(2c, #81)

- **날짜:** 2026-09-25
- **결정:** 부품·선을 옮기면(끌기, 방향키) 먼저 시험해 보고 기준을 지킬 때만 남긴다. `kr.ac.hallym.hcs.app.wiring.SafeMove`가 원조 `SelectTool`·방향키 이동의 끝에서 불린다(`// HCS:`, tools 층).
  - **시험 순서:**
    1. 선분 평행 이동(`SegmentDrag`): 선 하나만 골라 그 선과 수직으로 끌 때, 양쪽 끝에 붙은 수직 다리 하나씩이 늘거나 준다. 끝이 포트에 닿거나, T로 닿거나, 다리가 둘 이상이면 쓰지 않는다.
    2. 원조 연결 유지 이동: MoveGesture가 선을 늘리고 꺾는다. 원조가 길을 찾지 못하고 남긴 점과, 포트끼리 선 없이 바로 닿아 있던 점은 옮긴 포트에서 원래 자리까지 곧은 선으로 잇는다. 가로·세로가 아니면 ㄱ자로 잇되, 가로 먼저를 시험하고 안 되면 세로 먼저를 시험한다. (데모의 PC는 원조만으로는 D 연결을 잃었다.)
    3. 선 없이 옮기기: 원조 동작, 선택한 것만 옮긴다.
  - **남기는 기준:**
    - 1·2는 넷리스트(넷별 포트 집합)가 옮기기 전과 같아야 한다. 옮긴 부품의 포트는 옮기기 전 자리로 적어 비교하므로, 옮긴 부품의 연결도 그대로여야 한다.
    - 1·2는 새로 그은 선이 부록 A.4 출력 규칙(`WireRules`)을 지켜야 한다: 교차점에 끝점 없음, 목적 포트가 아닌 포트 위 통과 없음, 다른 선과 같은 직선 위 겹침 없음. T자 분기는 된다.
    - 3은 옮긴 부품의 포트를 뺀 넷리스트가 같아야 한다(다른 넷이 합쳐지거나 나뉘지 않음).
  - **결과:** 1이나 2가 남으면 조용히 끝난다. 3으로 옮기면 상태 표시줄에 "선을 따라오게 하면 다른 연결이 바뀌어, 선 없이 선택한 것만 옮겼습니다."를 보인다. 3도 어기면 옮기지 않고 "그 자리로 옮기면 다른 연결이 바뀌어 옮기지 않았습니다."를 보인다.
  - **시험은 복사한 회로에서:** 후보마다 회로를 복사해(부품은 새 복사본, 선은 같은 객체) 결과를 만들고 기준을 따진다. 실제 회로는 고른 후보를 적용할 때 한 번만 바뀐다. 처음에는 실제 회로에서 시험하고 되돌렸지만 선택이 흐트러지고(지운 선이 선택에서 빠짐) 변경 이벤트가 쓸데없이 흘렀다.
    - 서브회로 인스턴스 복사본은 서브회로의 사용처 목록에 올라가므로 따진 뒤 복사한 회로를 비운다.
  - **되돌리기:** 남긴 이동(원조 이동 + 더한 선)은 한 동작이다. 되돌리기 한 번에 이동과 선 변경이 함께 취소되고, 다시 실행도 한 번이다.
  - **테스트에서 발견한 것:** 헤드리스 테스트에서 이동·되돌리기를 되풀이하면 원조 `SmallSet`·`Circuit.getBounds`에서 ConcurrentModificationException이 났다. 원인은 시뮬레이터 전파 스레드가 테스트 스레드의 편집과 동시에 돈 것이다. 앱에서는 편집이 이벤트 스레드에서 일어난다. 테스트는 시뮬레이터를 멈추고 돈다. 멈춘 뒤 8번 × 24가지 이동·되돌리기에서 예외와 되돌리기 어긋남이 없었다.
- **테스트(`SafeMoveTest`):**
  - 규칙 검사기의 네 경우.
  - 다른 넷을 끝점 없이 가로지르는 이동, 다른 부품 포트 위로 길이 나는 이동, 다른 넷의 직선 위로 옮기는 선(거절), 꺾임이 다른 넷 선 위에 생기는 선분 이동(거절). 모두 다른 넷 불변과 A.4를 확인하고, 되돌리기 한 번에 원래대로 돌아오는지 본다.
  - 선분 평행 이동: 다리 둘이 따라오고 조각이 늘지 않는다.
  - demo-datapath의 PC·halt·Zero·regfile·alu·Data Memory를 네 방향으로 옮기고 매번 되돌린다(24번). 선이 따라오면 전체 넷리스트가 같고, 아니면 다른 넷이 같다. 되돌리기 한 번에 원래대로 돌아온다.
    - 지금 15번은 선이 따라오고, 핀(halt)은 늘 따라온다.
    - 못 따라오는 경우 1: regfile·alu처럼 포트가 20px 간격으로 붙은 상자를 포트 줄 방향으로 옮길 때. 한 포트의 곧은 길(ㄱ자)이 옆 포트의 옛 선 끝에 닿아 두 넷을 잇게 된다.
    - 못 따라오는 경우 2: 아래 변에 포트가 있는 부품(PC clk, Data Memory 제어)을 아래로 옮길 때. 옛 연결점이 옮긴 몸체 안에 들어가, 어떤 선도 몸체를 지나야 한다.
    - 이때는 선 없이 옮긴다. 묶음 전체를 다시 그리는 길 찾기는 원조도 실패하며, 4b 편의 기능에서 다시 본다.
  - **몸체 통과 금지(보기 규칙):** 새 선이 부품 몸체 안을 지나면(몸체를 3px 줄인 사각형과 겹침) 쓰지 않는다. 연결 규칙은 아니다. 하지만 선이 몸체를 가로지르면 학생이 연결을 잘못 읽는다(#81 스크린샷에서 clk 선이 PC 몸체를 지난 것을 발견). 터널·핀·프로브·스플리터·상수·클럭처럼 작은 부품은 보지 않는다.
  - **겹침 규칙:** 부록 A.4는 "다른 넷"과의 겹침을 금한다. 따라오는 선이 같은 넷의 옛 선 위를 지나는 것은 연결을 바꾸지 않으므로 허용한다(옮기기 전 넷으로 판단). 다른 넷과 겹치면 넷이 합쳐지므로 넷리스트 비교도 함께 막는다.
  - **길 찾기 결과가 그때그때 다른 것:** 원조 길 찾기(Connector)는 시간 제한이 있어 부하에 따라 결과가 다르다. 그래서 원조 결과를 쓰지 않고 옛 자리에서 곧은 선(ㄱ자)으로만 잇는 방법을 한 번 더 시험한다. 테스트 결과가 실행마다 같다.
- **이유:** 원조의 연결 유지 이동은 길을 찾다가 다른 선 위에 끝점을 두거나 남의 포트 위를 지나 넷을 합칠 수 있다. 사용자 요청(#81 주의)대로, 옮긴 부품의 연결 외에는 아무것도 바뀌지 않아야 한다.
- **대안:** 원조 이동을 그대로 두고 진단(합선)으로만 알리기. 학생이 모르는 사이 회로가 바뀐다.

## D-056 결정적 길 찾기(W-01)

- **결정:** 원조 이동 길 찾기(`com.cburch.logisim.tools.move.Connector`, tools 층이고 엔진 패키지 아님)를 결정적으로 바꾼다(`// HCS: W-01`).

  - 연결 목록을 HashSet 순서가 아니라 위치·방향으로 먼저 정렬한 뒤 원조의 순서 규칙(이동 방향 투영 정렬, 역순)을 적용한다.
  - 무작위 섞기는 시도 번호로 씨앗을 고정한 Random을 쓴다.
- **효과:** 같은 회로·같은 이동은 어느 PC에서나 같은 선을 만든다(체크리스트 8). demo-datapath 24가지 이동의 결과를 이동마다 고정한 표로 테스트한다. 임계값 비교는 없앴다.
- **이유:** 원조는 섞기에 씨앗이 없고 시간 제한이 있어, 부하와 실행마다 결과가 달랐다(#81에서 발견).
- **대안:** 원조 길 찾기를 쓰지 않기. 원조가 잘 잇는 경우까지 잃는다.

## D-057 따라온 선 정리와 고무줄 후보(W-02, W-03, S-03)

## D-059 새 선·부품을 자동으로 두는 편집의 검사기 하나(W-05)

- **날짜:** 2026-09-25
- **결정:** 붙이기(핀·상수·프로브·터널), 게이트 바꾸기, 선을 터널로, 빠른 Probe, 비트 뽑기·나누기·합치기, 스플리터 고치기는 모두 `WireGuard`를 거친다. 편집을 실제 회로에 한 번 해 보고 되돌린 뒤 네 가지를 본다.
  1. 새 선이 부록 A.4 출력 규칙(`WireRules.violations`)을 지킨다.
  2. 군더더기(`WireRules.clutter`)를 새로 남기지 않는다.
  3. 남은 옛 부품끼리의 넷이 합쳐지거나 갈라지지 않는다. 단, 기능이 뜻한 점(붙일 포트, 누른 선 위의 점, 바꿀 부품의 포트 자리)의 넷은 다른 넷과 이어져도 된다. 같은 이름 터널을 붙여 그 신호에 잇는 것은 학생이 이름으로 한 연결이다.
  4. 새 부품의 포트는 뜻한 점에서만 옛 선·포트에 닿는다(예: 합친 스플리터의 팔 끝이 옆 세로선 위에 오면 막는다).
  - 어기면 바꾸지 않고 상태 표시줄에 한 줄로 알린다(`edit.wireRules`). 통과하면 원조 `CircuitMutation.toAction` 그대로라 되돌리기 한 번에 취소된다.
  - 따라오는 선(옮기기)은 이미 `SafeMove`가 같은 `WireRules`로 본다. 복제는 사본이 떠 있다가 내려놓일 때 연결되므로 `SafeDuplicate`가 원조 자리에서 사본이 옛 선·포트에 닿거나 몸체가 겹치면, 원조와 같은 네모 나선 순서로 닿지 않는 가장 가까운 자리로 옮겨 내려놓는다(원조가 옮기기를 복제에 이어 붙여 되돌리기 한 번). 학생이 사본을 끌어 선 위에 두는 것은 학생의 배치라 막지 않는다.
  - 테스트는 기능마다 통과·막힘 경우를 고정 기대값으로 두고, 이 기능들을 부르는 소스가 모두 검사기를 거치는지 검사한다(`WireGuardTest`).
- **이유:** 체크리스트 2·7(선이 망가져 보이지 않게, 군더더기 없게)과 #81의 "뜻하지 않은 연결 금지"를 기능마다 따로 두지 않고 한 곳에서 지킨다.
- **대안:** 복사한 회로에서 시험하기(SafeMove 방식). 붙이기·바꾸기는 기존 부품 객체를 그대로 참조하는데, 원조는 부품을 다른 회로에 넣으면 서브회로 사용 관계를 옮겨 적어 원본이 망가진다. 실제 회로에서 해 보고 되돌리는 쪽을 택했다(파일 dirty 표시와 되돌리기 목록은 건드리지 않고, 선택은 되살린다).

## D-062 영향 경로(P-01)와 공용 연결 엔진 확장

- **날짜:** 2026-09-25
- **결정:**
  - **엔진:** 2b의 `Trace`(넷을 따라 앞·뒤로, 터널은 넷에서 합침, 서브회로는 안쪽 핀으로 들어가 바깥 포트로 나옴, 상태 부품에서 멈춤)를 넓혀 P-01과 P-07이 함께 쓴다. 새 엔진을 따로 만들지 않는다.
    - 비트 단위: 넷마다 따라가는 비트(BitSet)를 들고, 스플리터는 따라가는 비트가 가는 팔로만 건넌다. 부품을 건너면 출력 넷 전체 비트가 된다.
    - 깊이: 건넌 부품 수(스플리터·서브회로 경계는 세지 않음). 깊이별 넓이 우선이고, 같은 깊이 안 순서는 포트 위치(y, x), 부품 이름, 포트 번호라 결정적이다.
    - 걸음 목록(부품·스플리터·들어감·나옴), 사이클(상태 부품을 넘은 수, "Through Registers"로 넘은 곳은 다음 사이클), 고리 닫힘(이미 지난 조상 넷으로 돌아옴, 진단은 하지 않음), 건널지 묻는 고리(`Pass`, P-07 Active Path Only 자리)를 결과에 둔다.
  - **보기:** 켜면 나머지를 흐리게(흰색 반투명) 하고, 앞은 파랑 띠·뒤는 호박색 띠로 선을 강조하고, 닿은 선과 부품을 다시 선명하게 그린다(값 색 그대로). 시작 부품은 남색 굵은 테두리, 멈춘 상태 부품은 호박색 점선 테두리, 안쪽에 닿은 서브회로는 파랑 테두리와 "alu: 3 places" 칩이다. 같은 이름 터널은 닿은 넷의 터널을 선명하게 다시 그리고 얇은 테두리를 두르며, 터널이 딱 둘인 넷만 두 터널 사이를 점선으로 잇는다. 셋 이상이면 점선이 거미줄처럼 화면을 가로지르고(alu 안처럼 터널로 짠 회로), 클럭 넷은 데이터 흐름이 아니어서 잇지 않는다(첫 스크린샷에서 clk 점선이 데이터패스를 가로질렀다). 점선은 부품 몸체(터널 이름 포함)와 라벨 칩 위에서는 잘라 내어 글자를 가리지 않는다. 닿은 부품을 다시 선명하게 그릴 때는 원조 라벨 글자를 빼고 그린다(라벨 칩이 대신한다; 처음에는 Zero LED 라벨이 두 번 그려져 점프를 가렸다). 서브회로로 들어가면 그 안에서 닿은 곳을 계속 보인다(어느 인스턴스든).
  - **명령:** 우클릭 "Influence" 묶음(Show Influence (Forward / Backward / Both), Path Between Selected, Through Registers, Clear Influence). 키 I(앞), Shift+I(뒤), [ ](한 단계 좁히기·넓히기, 처음은 끝까지 보임), Esc(지우기). 기존 단축키와 겹치지 않는다(I·[·]는 비어 있었고, Esc는 영향 경로가 켜져 있을 때만 가로챈다). 상태 표시줄에 한 줄로 방향·단계를 알린다.

"저장하면 ripple_carry.circ의 fa0, fa1 연결 N곳이 끊깁니다"와 Save Anyway / Cancel(기본 Cancel). 원조 기본 모양은 핀을 지우면 남은 포트가 앞으로 당겨져 **옆 핀의 선에 닿아 조용히 잘못 이어진다.** 이것은 정적 진단이 알 수 없는 끊김이라(값은 흐른다), 저장 전 경고가 유일한 안내다. 그래서 PLAN.md 11.1의 "끊긴 곳은 진단에 남는다"를 "저장 전에 모두 세어 알린다"로 고쳤다. 아무것에도 닿지 않게 된 입력 포트는 기존 진단(연결되지 않은 서브회로 포트)이 그대로 보인다.

## D-067 읽는 포트 이름(S-09)

      - 게이트 입력은 1부터(`input 2`), 선택기류 입력은 선택 값과 같게 0부터(`input 0`), `select`·`enable`·`output`.
      - 원조 부품이 스스로 쓰는 짧은 포트 이름(D, Q, A, sel, Addr…)은 그대로다.
      - 라벨로 이름이 붙는 포트 하나짜리 부품(핀·터널)은 한 번만(`PC`).

- **이유:** 내부 이름이 찾기 결과에 그대로 보여 학생이 무엇인지 알기 어려웠다(S-09).

## D-068 화면 맞춤은 가로·세로 모두 가운데(S-10)

- **날짜:** 2026-09-26
- **결정:** 캔버스에 "원점 이동"(화면 px)을 둔다. 이것은 0보다 작은 스크롤과 같다.
  - **화면 맞춤:** 회로 영역(부품·선과 라벨 칩)이 보이는 영역보다 작은 축은 원점을 옮겨 가운데 두고 스크롤을 0으로 한다. 큰 축은 원점 이동 없이 스크롤로 가운데 둔다(`ZoomMath.fitPlacement`).
  - **커서 자리 배율:** 옮긴 원점을 뺀 가상 스크롤로 커서 아래 점을 고정한다. 새 가상 스크롤이 0보다 작으면 그만큼을 다시 원점 이동으로 둔다. 그래서 맨 위·왼쪽 가까이에서도 커서 아래 점이 그대로다.
  - **없앨 때:** 회로를 바꾸면 없앤다. 편집 중에는 그대로라 그림이 움직이지 않는다.
  - **한도(후속, P-07 검토 18o):** 원조 배율 조절이 보던 가운데를 지키며 두는 원점 이동은 회로 영역을 가운데 두는 만큼(`ZoomMath.originCap`)까지만이다. 작게 봤다가 다시 키우면 넓어진 회로 왼쪽·위에 빈 띠가 남았다. 커서 자리 배율은 커서 아래 점을 지키는 것이 먼저라 한도를 두지 않는다(빈 띠는 커서 바로 옆에만 생긴다).
  - **캔버스(`Canvas`, `CanvasPainter`, `GridPainter`의 HCS 줄):** 그림은 원점만큼 옮겨 그린다. 마우스 좌표, 다시 그리는 영역, 팝업 자리, 보이는 영역은 원점을 빼거나 더한다. 격자는 음수 영역에서도 이어지게 내림 나눗셈으로 바꿨다.
  - **HCS 쪽:** 원점이 필요한 곳(빠른 속성 창, 라벨 바로 고치기, 진단·찾기·다음 터널로 스크롤)은 `Canvas.hcsToScreen`, 반대(파일 탭 끌어 놓기, Ctrl+K가 마우스 자리를 모를 때의 보이는 영역 가운데)는 `Canvas.hcsToCircuit` 하나로 바꾼다. 원조 배율 조절(ZoomModel을 바로 바꿈)로 배율을 바꾸면, 원조 CanvasPane이 원점을 모르고 스크롤 범위가 바뀌기 전에 값을 넣어 가운데가 어긋나므로, 바뀌기 전에 보던 가운데를 새 배율에서 다시 가운데에 둔다(모자라면 원점 이동, 커서 배율과 같은 규칙). 다음 터널로 스크롤은 배율을 곱하지 않던 문제도 함께 고쳤다.
- **이유:** 체크리스트 11("화면 맞춤은 회로 전체를 가로·세로 모두 기준으로 여백을 두고 가운데 맞춘다"). 가로로 긴 데모 회로는 폭이 배율을 정해 위쪽에 붙고 아래 1/3이 비었다. 스크롤은 0보다 작아질 수 없어 원점을 옮기지 않고는 가운데 둘 수 없다.
- **대안:**
  - 캔버스를 가운데 두는 바깥 패널: 여백을 눌러도 캔버스에 닿지 않아 부품을 놓거나 선택을 풀 수 없다.
  - 늘 일정한 원점 여백("무한 캔버스"): 처음 화면이 원조와 달라진다.
  - 세로로 넘치게 배율을 올리기: 가로가 잘린다.

  - 속성 칸을 왼쪽으로 되돌리기: 2a에서 오른쪽으로 옮긴 결정(#74)과 어긋난다.

## D-073 기록 엔진: 넷 변화분 + 체크포인트 재실행(C-01)

- **날짜:** 2026-09-26
- **결정:** `kr.ac.hallym.hcs.app.record`의 `Recording`이 최상위 회로 하나의 시뮬레이션을 스텝(원조 틱 하나, 한 사이클 = 두 스텝)마다 기록한다. `Recorder`는 프로젝트의 원조 Simulator에 청취자로 붙는다.
  - **기록하는 것:** 서브회로 인스턴스 안까지 모든 넷(연결 엔진 `Netlist`의 넷마다 대표 자리 하나)의 값을 바뀐 것만 적는다. 같은 값은 한 객체를 함께 쓴다.
  - **지난 상태:** 회로 상태 전체를 체크포인트로 복제해 두고(`CircuitState.cloneState`, 원조 공개 API), 지난 스텝은 가장 가까운 앞 체크포인트에서 원조 엔진으로 다시 틱·전파해 만든다. 기록 재생이 곧 실제 재실행이다(테스트가 넷마다 비교한다).
  - **체크포인트:** 스텝 0, 64스텝마다, 입력을 바꾼 스텝마다 둔다. 최근 2048스텝 밖은 512스텝마다 하나로 줄이되 입력을 바꾼 스텝은 남긴다.
  - **새로 시작:** 리셋(원조 리셋은 전파 완료만 알리므로 리셋을 요청하는 네 곳이 `Recorder.requestReset`을 부른다. 원조 Simulate 메뉴는 `// HCS:` 한 줄)하면 스텝 0부터, 회로를 고치면(넷 구조가 바뀌어 옛 체크포인트를 쓸 수 없다) 지금 스텝부터 새로 적는다.
  - **보관 상한:** 100,000스텝(50,000사이클). 넘으면 오래된 스텝을 체크포인트 경계에서 버린다. 수치는 docs/PERFORMANCE.md.
- **이유:** PLAN.md 5.4. 어떤 신호가 필요할지 미리 알 수 없어 모든 넷을 적는다. 과거 회로 상태 전체(레지스터 내용, 메모리)를 모든 스텝마다 복제하면 메모리가 너무 크다. 넷 변화분(스텝당 약 0.4 KB)과 성긴 복제(하나 약 157 KB)를 섞으면 50,000사이클이 약 77 MB다. 엔진을 고치지 않는다(청취자와 공개 API만 쓴다).
- **대안:**
  - 스텝마다 회로 상태 전체를 복제: 스텝당 약 157 KB라 몇천 사이클이면 수백 MB다.
  - 넷 값만 적고 복원하지 않기: 레지스터·메모리 내용과 서브회로 안 상태가 없어 회로도를 그 사이클 값으로 보일 수 없다(C-03).
  - 원조 Logging(Simulate › Logging) 재사용: 고른 신호만 적고, 되돌리기가 없다.
